## 一、立场声明

> **AI 用于提效，不用于替代。**
> —— 架构书 六(二)，对应赛事手册 8.3

这句话是本项目的合规底线，也是评分维度。需要说清楚的是：**这不是「少用 AI」的意思**。赛事把「AI 工具使用」单列 25% 分值，架构书八章也把「深度使用平台的多智能体协作、长期记忆、Skills 生态、知识库四项核心能力」列为得分支撑 —— 说明**用得多是对的**。

边界不在「用量」，而在**责任归属**：

| 维度 | 提效（合规） | 替代（违规） |
| --- | --- | --- |
| **判断** | AI 给方案，人做选择并说明理由 | 直接采用 AI 结论，无人判断 |
| **内容** | AI 生成初稿，人审核修正 | 直接提交 AI 原文 |
| **责任** | 人能解释每一个技术决定的来龙去脉 | 「AI 说这样」成为唯一理由 |
| **边界** | 明确标注哪些来自 AI | 隐去 AI 参与，冒充人工产出 |

**一句话判据**：**如果评审问「这里为什么这么做」，你能给出 AI 之外的理由吗？** 能，就是提效；不能，就是替代。

## 二、AI 使用的四个层级

按「人对结果的介入深度」分级，级别越高合规风险越大。

| 级别 | 场景 | 人的介入 | 合规状态 | 留痕要求 |
| --- | --- | --- | --- | --- |
| **L1 辅助检索** | 让 AI 找资料、解释概念、翻译 | 人判断结果对不对 | ✅ 完全合规 | 常规提交，不需单独留痕 |
| **L2 草稿生成** | 让 AI 写初稿、给代码框架 | 人改写、裁剪、补逻辑 | ✅ 合规 | `AI-assisted` footer + 迭代记录 |
| **L3 深度协作** | 多轮对话迭代提示词、调优架构 | 人提出方向、判断取舍、迭代 | ✅ 合规且**受鼓励** | 完整迭代记录（**评审核心证据**） |
| **L4 直接采信** | 未经审核直接提交 AI 输出 | 无 | ❌ **违规** | — |

> **本项目的目标状态是 L3。** 架构书二(4)描述的「本地起草 → 平台验证 → 版本留痕」正是标准 L3 工作流：人在本地和平台之间反复迭代，每一次都有记录。评审看的就是这个过程的真实性与深度。

## 三、分场景使用规则

### 3.1 代码（自研 Skills、本地脚本）

| 允许 | 要求 |
| --- | --- |
| ✅ 用 AI 生成 Skills 框架 | 团队必须能逐行解释逻辑；关键路径建议加人工注释 |
| ✅ 用 AI 排查报错 | 需理解错误原因，不能只粘贴修复代码了事 |
| ✅ 用 AI 写数据处理脚本 | 必须人工验证输出结果的正确性 |
| ❌ 直接提交未经运行的 AI 代码 | 架构书三(1)要求每个 Skill 有明确失败处理，AI 很少主动考虑边界 |

**特别提醒**：架构书三(2)明确要求定时任务「失败处理：抓取失败时降级为『本次暂无可更新内容』并记录，不阻塞用户其他操作」。这类**降级逻辑必须人工检查**，AI 默认生成的代码通常直接抛异常。

### 3.2 提示词（`prompts/`）

提示词是本项目最核心的资产，**鼓励深度使用 AI 迭代**，但要求完整留痕。

| 要求 | 说明 |
| --- | --- |
| 分层编写 | 按架构书二(4)的角色层/原则层/任务层/上下文层组织，不要让 AI 生成一整段大提示词 |
| 平台验证 | 每个提示词版本需在 LearnBuddy 上实测，记录 `platform_validated_at` |
| 迭代说明 | front matter 的 `迭代说明` 表格逐版记录「改了什么 + 验证结果」 |
| 禁止 | 直接把某个公开提示词库的内容搬来当自己的 —— 属学术诚信问题 |

### 3.3 知识库内容（`knowledge/`）

| 允许 | 要求 |
| --- | --- |
| ✅ 用 AI 辅助提炼论文要点 | **必须**人工核对原文，防止 AI 幻觉出不存在的方法或数据 |
| ✅ 用 AI 生成摘要初稿 | 人工改写为符合知识单元格式的内容 |
| ❌ 让 AI 编造文献信息 | **严重违规**。`source.url` 必须真实可访问 |
| ❌ 把 AI 生成内容当作原始文献 | 知识库承载的是「文献提炼」，不是「AI 观点」 |

> **强制规则**：`knowledge/domains/` 下每个知识单元的 `source` 字段，**必须由人工逐一访问 `url` 确认可达且内容匹配**。这条规则没有例外 —— 架构书三(4)的语料准入标准要求「来源可公开访问、有明确作者与出处」，AI 生成的虚假引用是本项目最大的合规风险点。

### 3.4 Web 展示层（`web/`）

架构书四(2)明确 Web 入口「不实现独立的智能体逻辑」，四(3)说明选择「智能体为主、Web 为辅」的理由。因此：

| 允许 | 禁止 |
| --- | --- |
| ✅ 用 AI 生成 HTML/CSS/JS | ❌ 在 Web 侧调用大模型 API（架构书五(3)排除项） |
| ✅ 用 AI 调 ECharts 图表配置 | ❌ 让 Web 承担智能体职责 |
| ✅ 用 AI 优化响应式布局 | ❌ 引入重型框架（架构书五(3)排除项） |

### 3.5 文档与规范（`docs/`）

| 允许 | 要求 |
| --- | --- |
| ✅ AI 辅助生成文档框架 | 条款必须结合项目实际修改，不能是通用模板 |
| ✅ AI 辅助检查格式一致性 | 最终判断由人做 |
| ❌ 直接提交未经审阅的 AI 文档 | 尤其规范类文档，条款会约束团队行为 |

## 四、知识边界与学术诚信

架构书六(2)列出五条合规设计要点，逐条落实：

| 合规要点（架构书原文） | 落地措施 | 责任目录 |
| --- | --- | --- |
| **知识边界声明**：智能体在超出知识范围时必须显式声明，不得推测性作答 | 写入 `prompts/principle/` 原则层；输出无出处时须声明 | `prompts/` |
| **出处标注**：所有学术内容附来源，便于用户核验 | JSON Schema 强制 `source.url` 必填；Markdown 文末必须有参考来源段 | `data/`、`knowledge/` |
| **可见度控制**：个人资产遵循平台权限体系，默认私密 | `visibility` 字段默认值 `private` | `data/assets/` |
| **知识产权**：第三方库与开源资源在文档中注明；作品按开源协议发布 | 第三方清单见本文 §5；根目录 MIT LICENSE | 全仓 |
| **AI 使用边界**：严格遵守手册 8.3，AI 用于提效而非替代，保留完整迭代记录 | 本规范全文 + `iteration-log/` | 全仓 |

### 4.1 方法论助手的特殊约束

架构书二(3)对「领域方法论助手」有明确合规要求，**必须原文遵守**：

> 「该助手在交互中**不得以『某位专家本人』的口吻发言或暗示获得授权**，须明确告知用户其方法论提炼自公开学术资源。这一约束既是学术诚信的要求，也规避了肖像权与署名权风险。」

具体检查点：

- [ ] 交互中**不出现**「我是 XX 教授」「XX 老师认为」这类拟人化表述
- [ ] **明确告知**用户：内容提炼自公开学术资源，不代表任何个人观点
- [ ] 若引用具体学者观点，**必须**标注原始出处
- [ ] 避免使用真人姓名、肖像、签名等可能引发肖像权与署名权风险的元素

> 架构书同时给出降级/升级路径：若后续获得真人导师参与与校准，可在**不改动架构**的前提下升级为正式专家分身形态。在此之前，须严格执行上述公开资源路线。

## 五、第三方资源登记

架构书六(2)要求「使用的第三方库与开源资源在文档中注明」。所有引入的第三方资源**必须**登记在 `docs/第三方资源清单.md`：

| 登记字段 | 说明 |
| --- | --- |
| 名称与版本 | 如 `ECharts 5.5.0` |
| 来源链接 | 官方仓库或官网 |
| 许可证 | 如 Apache-2.0、MIT |
| 用途 | 在本项目中的具体作用 |
| 是否修改 | 若修改源码需说明 |

**当前已登记资源**（依据架构书选型）：

| 名称 | 许可证 | 用途 | 架构书出处 |
| --- | --- | --- | --- |
| ECharts | Apache-2.0 | 路线图与图表可视化 | 五(二) 图表可视化 |
| LearnBuddy 平台 | 赛事指定平台 | 承载全部智能体能力 | 五(一) 智能体平台 |
| Python | PSF License | 自研 Skills 与本地脚本 | 五(一) 编程语言 |

> 许可证兼容性提醒：本项目采用 MIT 发布，引入的第三方资源须为 MIT/Apache-2.0/BSD 等宽松许可。**避免引入 GPL/AGPL 类传染性许可的库** —— 会与 MIT 开源发布产生冲突。

## 六、留痕的执行要求

架构书六(2)最后一句话是全文最关键的约束：

> 「**保留完整迭代记录以备评审**」

这句话在工程上意味着三件必须做的事：

### 6.1 记录什么

`iteration-log/YYYY-MM-DD-<主题>.md` **必须**包含：

| 节 | 内容 | 为什么必须 |
| --- | --- | --- |
| 元信息 | 时间、执行人、AI 工具、会话标识 | 证明记录真实性 |
| 迭代目的 | 这一轮想解决什么问题 | 证明是有目标的使用，非盲目尝试 |
| **原始提示词** | 全文复制，不做美化 | **核心证据**，展示提问质量 |
| **AI 关键输出** | 摘录重要回复（可截断长内容） | 展示协作过程 |
| **人工调整** | 改了什么、为什么改 | **证明「提效非替代」的关键** |
| 结论与产物 | 最终落地到哪些文件 | 建立与提交记录的关联 |

### 6.2 记录原则

| 原则 | 说明 |
| --- | --- |
| **只增不删** | 记录一旦归档不得修改、删除、重写 |
| **保留失败** | 失败的尝试也要记录 —— **失败记录比成功记录更能证明使用深度** |
| **不做美化** | 不要事后把提示词润色得像模板，真实过程才有说服力 |
| **及时归档** | 迭代结束后 24 小时内，避免事后凭记忆补写 |

> **关于失败记录**：很多团队只记成功路径，这恰恰让评审怀疑真实性 —— 真实的 AI 协作一定充满反复。记录「AI 第一次生成的方案有 X 问题，我调整提示词后转向 Y」远比「我提问，AI 给出完美答案」有说服力。

### 6.3 与提交的关联

含 AI 生成内容的提交，**必须**在 footer 标注：

```text
feat(skill): 新增简报生成 Skill 的相关性排序

将检索结果按 high/medium/low 三层排序，
高相关内容优先展示，对应架构书四(二)的展示要求。

AI-assisted: LearnBuddy, session-2026-09-20-02
Refs: 迭代记录 2026-09-20-简报生成Skill.md
Reviewed-by: <人名>
```

`AI-assisted` 中的会话标识应与 `iteration-log/` 中的记录对得上。

## 七、禁止事项清单

以下行为**明令禁止**，违反将影响作品合规性：

| # | 禁止行为 | 后果 |
| --- | --- | --- |
| 1 | 直接提交未经人工审核的 AI 生成代码/文档 | 违反「提效而非替代」 |
| 2 | 让 AI 编造文献、作者、期刊、DOI 或 URL | 严重学术不端 |
| 3 | 提交无法解释「为什么这么做」的技术方案 | 无法证明工程完整性与 AI 使用深度 |
| 4 | 隐去 AI 参与事实，声称全人工完成 | 与手册 8.3 直接冲突 |
| 5 | 以「某位专家本人」口吻输出方法论助手内容 | 违反架构书二(3)合规要求，涉肖像权与署名权风险 |
| 6 | 将真实用户画像/学习轨迹/个人资产提交到公开仓库 | 违反数据分类与隐私要求 |
| 7 | 在仓库中硬编码 API Key、Token | 安全事故 |
| 8 | 删除或重写已有 `iteration-log/` 记录 | 毁坏评审举证材料 |
| 9 | 在 Web 侧独立调用大模型 API | 违反架构书五(3)排除项 |
| 10 | 引入 GPL/AGPL 类传染性许可的第三方库 | 与 MIT 发布协议冲突 |

## 八、AI 使用自查清单

### 提交前

- [ ] 我能解释这次提交中每一处技术选择的理由（除「AI 这么说」以外）
- [ ] 含 AI 生成内容的提交已加 `AI-assisted` footer
- [ ] 代码已在本地运行验证，非直接粘贴
- [ ] 知识单元的 `source.url` 已人工访问确认可达

### 每轮迭代

- [ ] `iteration-log/` 已归档，含原始提示词与人工调整说明
- [ ] 失败的尝试也已记录
- [ ] 提示词变更已在 front matter 中更新 `version` 与验证状态

### 提交作品前

- [ ] 全部 `iteration-log/` 完整，可还原 AI 使用全过程
- [ ] `docs/第三方资源清单.md` 完整，无传染性许可
- [ ] 方法论助手输出中无拟人化专家表述
- [ ] 仓库中无真实个人数据、无密钥
- [ ] 能回答「AI 帮你做了什么」与「你自己做了什么」且证据充分
