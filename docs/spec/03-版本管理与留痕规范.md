# SPEC-03 版本管理与版本留痕规范

> 文档编号：SPEC-03
> 文档版本：V1.0
> 生效日期：2026-09-18
> 上游依据：架构书 二(四) 提示词工程策略、五(一) 版本管理选型、六(二) 合规设计要点

---

## 一、为什么 10 天项目也需要版本管理

架构书五(1)给出选型「**Git + GitHub / Gitee** —— 满足手册源代码仓库要求」，六(2)要求「**AI 使用边界**：严格遵守手册 8.3，AI 用于提效而非替代，**保留完整迭代记录以备评审**」。

这两条合起来说明：**版本管理在本项目中有双重身份**。

| 身份 | 服务对象 | 说明 |
| --- | --- | --- |
| **工程基础设施** | 团队自己 | 代码与文档的变更管理、冲突解决、回滚 |
| **评审举证材料** | 赛事评审 | AI 使用深度（25%）与工程完整性评分需要过程证据 |

因此本规范不追求大厂级的严谨流程，而是**在 10 天内可执行的前提下，最大化留痕质量**。

## 二、仓库与平台策略

### 2.1 主仓 + 镜像

| 项 | 选定 | 理由 |
| --- | --- | --- |
| **主仓** | GitHub（Public） | 手册第 4 步要求 GitHub 公开仓库 + MIT License；在线部署服务多需绑定 GitHub |
| **镜像** | Gitee（同步） | 解决国内访问速度；评审若在国内可直接访问 |
| **协议** | MIT | 手册第 4 步推荐；已放根目录 `LICENSE` |
| **可见性** | Public | 手册硬性要求「GitHub 仓库必须设为公开」 |

> ⚠️ **公开仓库不等于可以放任何东西。** 用户画像、学习轨迹、个人资产属架构书六(1)的「中」敏感级，**真实数据一律不入库**，见 SPEC-02 §7。

### 2.2 镜像同步

Gitee 镜像采用**单向同步**（GitHub → Gitee），不做双向，避免循环同步与冲突：

```bash
# 一次性配置
git remote add gitee git@gitee.com:<org>/<repo>.git

# 每次推送主仓后同步
git push origin main
git push gitee main
```

也可在 Gitee 仓库设置中使用「仓库镜像管理」功能自动拉取，推荐后者（零维护）。

## 三、分支模型

采用**精简 GitHub Flow**，只有一个长期分支。10 天周期不支持 Git Flow 的多分支并行。

| 分支 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 长期主干，**始终可交付** | 永久 |
| `feat/<主题>` | 新功能（如 `feat/briefing-skill`） | 合并后删除 |
| `fix/<主题>` | 缺陷修复（如 `fix/radar-cron`） | 合并后删除 |
| `docs/<主题>` | 纯文档变更（如 `docs/format-spec`） | 合并后删除 |
| `hotfix/<主题>` | 演示前紧急修复 | 合并后删除 |
| `release/v<版本>` | 提交前冻结版本，仅用于打标签 | 提交后保留 |

### 合并规则

| 目标 | 方式 | 要求 |
| --- | --- | --- |
| 功能分支 → `main` | **Squash Merge** | 保持 `main` 历史线性，一个功能一个提交 |
| `hotfix` → `main` | Merge Commit | 保留修复过程的完整痕迹 |

> **为什么用 Squash**：10 天周期内会产生大量「改一下」「再改一下」的中间提交，Squash 让 `main` 的历史对评审友好。但中间过程并未丢失 —— 它保留在功能分支与 PR 记录中。

### 分支命名正则（CI 校验）

```regex
^(feat|fix|docs|hotfix|release)/[a-z0-9-]+$
```

## 四、提交信息规范

采用 [Conventional Commits](https://www.conventionalcommits.org/) 精简版。

### 4.1 格式

```text
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

### 4.2 type 取值

| type | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新增功能 | `feat(skill): 新增论文精读 Skill` |
| `fix` | 缺陷修复 | `fix(web): 修复路线图节点重叠` |
| `docs` | 文档变更 | `docs(spec): 补充 JSON 字段命名约定` |
| `data` | 数据文件变更（**本项目特有**） | `data(briefing): 更新 09-20 简报` |
| `prompt` | 提示词变更（**本项目特有**） | `prompt(radar): 增加相关性分层要求` |
| `refactor` | 重构（不改行为） | `refactor(kb): 拆分知识库加载逻辑` |
| `chore` | 杂务（配置、依赖） | `chore: 更新 commitlint 配置` |
| `revert` | 回滚 | `revert: 回滚简报生成逻辑变更` |

> `data` 与 `prompt` 是本项目自定义类型。**提示词是核心资产**，其变更必须独立可检索，因此单列 `prompt` 类型，便于事后统计「提示词迭代了多少轮」——这正是评审关心的「AI 使用深度」。

### 4.3 scope 取值（受控词表）

| scope | 覆盖范围 |
| --- | --- |
| `spec` | `docs/spec/` |
| `adr` | `docs/decisions/` |
| `kb` | `knowledge/` |
| `skill` | `skills/` |
| `prompt` | `prompts/` |
| `web` | `web/` |
| `data` | `data/` |
| `config` | `configs/` |
| `log` | `iteration-log/` |
| `repo` | 仓库级（`.gitignore`、`LICENSE` 等） |

### 4.4 subject 规则

- 中文描述，**不超过 50 字**；
- 动词开头，描述「做了什么」而非「改了什么文件」；
- 结尾**不加句号**；
- 不要写「修改」「更新」这类无信息量的词 —— 要说明改了什么内容。

| ✅ 正例 | ❌ 反例 |
| --- | --- |
| `feat(skill): 新增简报生成 Skill 的相关性排序` | `更新了一下` |
| `prompt(route): 补充分阶段路线的输出格式约束` | `改提示词` |
| `docs(spec): 明确 data 目录禁止手工编辑` | `update docs` |

### 4.5 footer：留痕的关键

以下情况**必须**在 footer 中标注：

| footer | 何时使用 | 示例 |
| --- | --- | --- |
| `Refs:` | 关联待办/需求 | `Refs: 建立项目仓库与文档规范` |
| `Reviewed-by:` | 有人工复核 AI 产出 | `Reviewed-by: 张三` |
| `AI-assisted:` | 该提交含 AI 生成内容 | `AI-assisted: LearnBuddy, session-2026-09-18-01` |
| `Breaking:` | 破坏性变更 | `Breaking: briefing JSON 字段重命名` |

> **`AI-assisted` footer 是硬性要求。** 凡提交中含有 AI 生成的内容（代码、提示词、文档），**必须**标注来源会话标识，与 `iteration-log/` 中的记录对应。评审据此可验证 AI 使用的真实性 —— 这直接服务于架构书六(2)「保留完整迭代记录以备评审」。

## 五、版本号规范

### 5.1 仓库版本

采用**语义化版本** `vMAJOR.MINOR.PATCH`：

| 位 | 递增条件 | 本项目示例 |
| --- | --- | --- |
| MAJOR | 交付形态不兼容变更 | `v1.0.0` 初赛提交 → `v2.0.0` 决赛重构 |
| MINOR | 新增能力（向后兼容） | `v1.1.0` 新增一个自研 Skill |
| PATCH | 修复与数据更新 | `v1.0.1` 修复简报排序错误 |

### 5.2 四类版本号并存，勿混淆

本项目有四套版本号，各自独立，**必须**在文档中写清是哪一套：

| 版本体系 | 格式 | 载体 | 示例 |
| --- | --- | --- | --- |
| **仓库版本** | `vX.Y.Z` | Git Tag | `v1.0.0` |
| **文档版本** | `V主.次` | 文档头部 | `V1.0` |
| **提示词版本** | `V主.次` | front matter `version` | `V1.2` |
| **Schema 版本** | 字符串 `"X.Y"` | JSON 字段 `schema_version` | `"1.0"` |

> 例：SPEC-02 文档版本 `V1.0`，其定义的 Schema 版本 `"1.0"`，二者当前数值相同但**含义不同**，前者是文档修订号，后者是数据结构契约号。

### 5.3 Git Tag

```bash
# 带注释的标签（必须用 -a，附说明）
git tag -a v1.0.0 -m "初赛提交版本：三项核心能力闭环可用"
git push origin v1.0.0
```

标签命名正则：`^v\d+\.\d+\.\d+$`

## 六、版本留痕体系

这是本规范的**核心章节**，直接服务于评审举证。

### 6.1 五类留痕载体

| 载体 | 记录什么 | 位置 | 模板 | 更新时机 |
| --- | --- | --- | --- | --- |
| **① 提交信息** | 每次变更的内容与原因 | Git 历史 | `commit-message.template.txt` | 每次提交 |
| **② 变更日志** | 面向使用者的功能变化 | `CHANGELOG.md` | `CHANGELOG.template.md` | 每次发版 |
| **③ AI 迭代记录** | AI 使用过程与人工调整 | `iteration-log/` | `iteration-log.template.md` | 每轮迭代 24h 内 |
| **④ 架构决策记录** | 重要取舍的理由 | `docs/decisions/` | `decision-record.template.md` | 决策发生时 |
| **⑤ 发布说明** | 面向评审的版本亮点 | GitHub Release | `release-note.template.md` | 每次打标签 |

### 6.2 CHANGELOG 规范

采用 [Keep a Changelog](https://keepachangelog.com/) 结构，六类条目：

| 分类 | 含义 |
| --- | --- |
| `Added` | 新增能力 |
| `Changed` | 行为变更 |
| `Deprecated` | 即将废弃 |
| `Removed` | 已移除 |
| `Fixed` | 缺陷修复 |
| `Security` | 安全与合规相关（**本项目须记录数据分类相关变更**） |

规则：
- 只记**面向使用者可见**的变更，不记内部重构细节；
- `[Unreleased]` 段落常驻，积累当前未发版变更；
- 版本标题格式 `## [v1.0.0] - 2026-09-26`；
- 每条变更末尾附提交短哈希（可选但推荐）。

### 6.3 AI 迭代记录规范（评审关键）

这是唯一**由赛事评分直接驱动**的留痕，占分 25%。要求如下：

| 项 | 要求 |
| --- | --- |
| 命名 | `iteration-log/YYYY-MM-DD-<主题>.md` |
| 粒度 | 一轮完整迭代一份（如「生成主控智能体提示词」为一轮） |
| 必含字段 | 时间、执行人、AI 工具与会话标识、迭代目的 |
| **必含证据** | **原始提示词全文** + **AI 关键输出摘录** |
| **必含反思** | 人工做了哪些修改、为什么改 —— 证明「AI 用于提效而非替代」 |
| 归档时限 | 迭代结束后 24 小时内 |
| 修改规则 | **只增不删**。补充用追加段落，不重写原文 |

> **为什么要记录「人工修改」**：架构书六(2)与手册 8.3 都强调 AI 用于提效而非替代。如果记录中只有「我让 AI 生成了 X，然后它就是 X」，反而证明使用深度不足。**真正有说服力的记录是**：「AI 生成了 X，但 X 在 Y 场景下会出错（附具体表现），我改为 Z，理由是……」——这体现了人对 AI 输出的判断与驾驭。

### 6.4 ADR 规范（架构决策记录）

架构书本身就包含「关键架构决策」章节（一(四)），本仓库把这类决策延续到工程实践中。

**何时必须写 ADR**：

- 引入或排除某项技术选型；
- 数据结构（JSON Schema）的破坏性变更；
- 目录结构的重大调整；
- 与架构书既有约定不一致的偏离（**必须**说明理由）。

**格式要点**：

| 节 | 内容 |
| --- | --- |
| 状态 | `提议` / `已接受` / `已废弃` / `被取代` |
| 背景 | 面临什么问题 |
| 决策 | 做了什么选择 |
| 理由 | 为什么这样选 |
| 备选方案 | 考虑过什么，为何不选 |
| 影响 | 正面与负面后果 |

**不可变规则**：已接受的 ADR **不删除、不改写**。被推翻时新增一条 ADR，并在旧条目的状态行标注 `被取代 by ADR-XXXX`。

### 6.5 留痕的完整链条示例

一次「新增简报生成 Skill」的完整留痕：

```text
① 迭代记录  iteration-log/2026-09-20-简报生成Skill.md
              └─ 记录了向 LearnBuddy 提问的原始提示词 + 输出 + 人工调整
② 分支      feat/briefing-skill
③ 提交      feat(skill): 新增简报生成 Skill 的相关性排序
              └─ footer: AI-assisted: LearnBuddy, session-2026-09-20-02
④ PR        含评审意见与修改过程
⑤ ADR       docs/decisions/ADR-0003-简报按相关性分三层.md（若涉及结构决策）
⑥ CHANGELOG [Unreleased] → Added 段落新增一行
⑦ Release   打 tag 时在 Release Note 中汇总
```

评审可以从 ⑦ 一路追溯到 ①，完整看到「需求 → AI 辅助 → 人工判断 → 落地 → 发布」的全过程。**这条链断了任何一环，举证力度都会下降。**

## 七、CI 边界：只校验，不构建

**架构书五(3)明确排除「生产级监控、CI/CD 流水线」**，理由是「初赛只需演示与在线可访问，不投入生产化建设」。本仓库严格遵守这一边界。

| 允许（轻量校验） | 禁止（明确排除） |
| --- | --- |
| ✅ JSON Schema 校验 | ❌ 自动构建产物 |
| ✅ YAML 语法校验 | ❌ 自动部署到生产环境 |
| ✅ 提交信息格式校验 | ❌ 生产级监控与告警 |
| ✅ 疑似密钥正则扫描 | ❌ 多环境发布流水线 |
| ✅ Markdown 链接可达性（可选） | ❌ 容器镜像构建与编排 |

> 判据很简单：**这条 CI 是在帮我们避免低级错误，还是在替我们做部署？** 前者加，后者不加。

## 八、提交与留痕检查清单

### 每次提交

- [ ] 提交信息符合 `<type>(<scope>): <subject>` 格式
- [ ] type 与 scope 在受控词表内
- [ ] 含 AI 生成内容的提交已加 `AI-assisted:` footer
- [ ] 未提交密钥或真实个人数据

### 每次合并

- [ ] 分支命名符合正则
- [ ] 功能分支到 `main` 使用 Squash Merge
- [ ] PR 描述完整（用 PR 模板）
- [ ] 若涉及架构取舍，已新增 ADR

### 每次迭代

- [ ] `iteration-log/` 已归档，含原始提示词与人工调整说明
- [ ] `CHANGELOG.md` 的 `[Unreleased]` 已更新
- [ ] 提示词文件 front matter 的 `version` 与 `迭代说明` 已同步

### 每次发版

- [ ] 版本号符合语义化规则
- [ ] `CHANGELOG.md` 的 `[Unreleased]` 已转为版本段落
- [ ] 已打带注释的标签并推送
- [ ] 已发布 GitHub Release
