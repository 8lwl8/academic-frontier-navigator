# SPEC-01 目录结构规范

> 文档编号：SPEC-01
> 文档版本：V1.0
> 生效日期：2026-09-18
> 上游依据：架构书 一(二) 总体分层（三横一纵）、五(一)(二) 技术栈、五(三) 明确排除项

---

## 一、设计依据：目录结构即架构图的落地

架构书一(二)给出「三横一纵」分层：**交互层 / 智能体层 / 能力层 / 数据层**，外加贯穿全层的**安全与合规**。目录结构必须让这四层在文件系统上有明确的物理归属，否则分层只是 PPT 上的概念。

| 架构层级 | 承载内容（架构书原文） | 本仓库对应目录 |
| --- | --- | --- |
| **交互层** | 对话交互、路线图可视化、简报呈现 | `web/`、`data/` |
| **智能体层** | 主控与三个领域子智能体、任务分解与协同 | `prompts/` |
| **能力层** | Skills 组件、定时任务、长期记忆、知识库检索 | `skills/`、`configs/` |
| **数据层** | 领域知识库、用户画像、学习轨迹、知识资产 | `knowledge/` |
| **纵向 · 安全合规** | 知识边界声明、出处标注、权限与可见度 | `docs/spec/04-*`、`.gitignore` |

> 一个刻意的设计：**没有 `src/`、`app/`、`backend/` 这类传统工程目录。** 因为架构书五(三)已明确排除自建后端、重型前端框架与生产级基础设施，预留这些目录只会诱导团队写出被明确排除的东西。目录结构本身就应该表达技术栈的边界。

## 二、完整目录树

```text

├── README.md                          # 仓库首页：定位、技术栈、快速开始

├── schemas/                           # 【格式契约】JSON Schema 校验文件

├── configs/                           # 【配置】YAML 配置与工具链配置

├── knowledge/                         # 【数据层】知识库，对应架构书三(四)

├── data/                              # 【交互层数据源】Web 只读消费的静态 JSON

│   ├── briefing/                      #   每日简报数据（对应 Web「前沿简报」页）
│   └── assets/                        #   知识资产数据（对应 Web「知识资产」页）
│
├── web/                               # 【交互层】只读展示，对应架构书四(二)
│   ├── index.html                     #   单页入口，不引入重型框架
│   ├── styles/                        #   CSS
│   ├── scripts/                       #   原生 JavaScript + ECharts 调用
│   └── assets/                        #   图片、图标等静态资源
│
├── iteration-log/                     # 【AI 使用留痕】评审举证材料，只增不删
```

## 三、逐目录职责说明

### `docs/` — 人读的长期文档

| 子目录 | 放什么 | 不放什么 |
| --- | --- | --- |
| `spec/` | 规范正文，编号 `NN-标题.md` | 临时笔记、待办 |
| `decisions/` | ADR，命名 `ADR-NNNN-标题.md` | 已被推翻的旧 ADR **不删除**，改为标记 `Superseded by ADR-XXXX` |
| `assets/` | 架构图、流程图源文件与导出图 | 大体积视频（放网盘，此处只放链接） |

**ADR 编号规则**：四位数字，从 `0001` 起递增，**永不复用**。即使某条 ADR 被废弃，其编号也保留，后继决策使用新编号。

### `knowledge/` — 数据层知识库

严格对应架构书三(四)的分库结构，**三库不得混放**：

| 子库 | 内容来源（架构书原文） | 服务对象 | 文件格式 |
| --- | --- | --- | --- |
| `domains/` | 顶会论文、经典教材、综述文章、公开课材料、开源项目文档 | 路线规划、论文精读 | Markdown 知识单元 |
| `intelligence/` | 每日抓取的论文与项目动态 | 前沿雷达 | JSON（结构化简报） |
| `personal/` | 用户阅读笔记、对话结论、学习轨迹 | 知识管家 | Markdown |

> **语料准入（架构书三(四)）**：来源可公开访问、有明确作者与出处、属于该领域奠基性或代表性成果、时效性满足要求。低质量或来源不明的语料不入库。`domains/` 下的每个知识单元**必须**在 front matter 中填写 `source` 字段（见 SPEC-02 §3.2）。

> ⚠️ **`knowledge/personal/` 默认不提交真实个人数据。** 该目录在 `.gitignore` 中按 `*.private.md` 模式屏蔽真实用户数据，仓库内只保留脱敏样例。原因见 SPEC-02 §7 数据分类。

### `prompts/` — 智能体层分层提示词

对应架构书二(四)的分层提示词架构，四层各占一个目录：

| 子目录 | 对应架构书层次 | 内容 |
| --- | --- | --- |
| `role/` | 角色层 | 身份、专业边界、能力声明 —— 定义智能体是谁、能做什么、不能做什么 |
| `principle/` | 原则层 | 探讨式引导、承认知识边界、可溯源、学术诚信 —— 跨场景恒定约束 |
| `task/` | 任务层 | 各子智能体的具体工作流与输出格式 —— 因任务而异 |
| `context/` | 上下文层 | 用户画像、当前研究方向、历史交互摘要 —— 由长期记忆动态注入 |

**命名规则**：`<层次>-<对象>.md`，例如 `role-主控智能体.md`、`task-前沿雷达.md`、`principle-通用约束.md`。

**文件头部必须包含版本信息块**（格式见 SPEC-02 §3.4），记录该提示词的版本与验证状态 —— 这是架构书二(四)「本地起草 → 平台验证 → 版本留痕」流程中「留痕」环节的载体。

### `skills/` — 能力层自研组件

对应架构书三(一)规划的四类自研 Skills：论文精读、路线生成、简报生成、资产提炼。每个 Skill 一个独立目录（名称用 kebab-case）：

```text
skills/
├── paper-deep-read/          # 论文精读
├── route-generate/           # 路线生成
├── briefing-generate/        # 简报生成
└── asset-extract/            # 资产提炼
```

**架构书三(一)硬性要求**：「每个 Skills 须有明确的输入契约、输出格式与失败处理策略。」因此每个 Skill 目录下的 `README.md` **必须**包含这三节，缺失视为未完成。

| 节 | 内容 | 检查点 |
| --- | --- | --- |
| 输入契约 | 参数名、类型、必填性、取值范围 | 与调用方约定一致 |
| 输出格式 | 结构示例 + 对应 JSON Schema 路径 | Schema 文件真实存在 |
| 失败处理 | 各类失败场景的降级行为 | 符合架构书三(二)「不阻塞用户其他操作」 |

### `data/` — Web 只读数据源

架构书四(二)明确 Web 侧「数据来自智能体输出结果的落地存储（静态数据文件或轻量存储服务），不做实时双向同步」。本仓库采用**静态 JSON 文件**方案。

| 子目录 | 对应 Web 页面 | 数据来源 |
| --- | --- | --- |
| `route/` | 学习路线 | 路线规划智能体输出的结构化数据 |
| `briefing/` | 前沿简报 | 前沿雷达智能体输出的简报数据 |
| `assets/` | 知识资产 | 知识管家沉淀的知识条目 |

**文件命名**：`<类型>-<标识>.json`，简报按日期 `briefing-YYYY-MM-DD.json`。

> **单向依赖铁律**：`data/` 由智能体输出导出生成，`web/` 只读消费 `data/`。**禁止 `web/` 直接读 `knowledge/`，也禁止手工编辑 `data/` 中的文件** —— 手工编辑会导致数据无法溯源，一旦评审追问「这个数字哪来的」就无法回答。生成脚本放 `scripts/`。

### `web/` — 交互层只读展示

技术栈由架构书五(二)锁定：**HTML + CSS + 原生 JavaScript + ECharts，无构建工具**。

| 约束 | 说明 |
| --- | --- |
| 不引入重型 SPA 框架 | 架构书五(三)明确排除，收益低于学习与调试成本 |
| 无构建步骤 | 直接浏览器打开 `index.html` 即可预览，降低环境复杂度 |
| 不独立调用大模型 API | 架构书五(三)明确排除，避免能力分散与算力重复消耗 |
| 所有条目标注出处链接 | 架构书四(二)要求「所有条目均标注出处链接」 |

### `iteration-log/` — AI 使用留痕

**这是全仓库唯一一个「只增不删」的目录**，承担评审举证职责（AI 工具使用占评分 25%）。

- 命名：`YYYY-MM-DD-<主题>.md`
- 模板：`templates/iteration-log.template.md`
- 归档时限：每轮迭代结束后 **24 小时内**
- 禁止行为：删除、覆盖、重写历史记录。补充说明用追加段落，不改原文。

### `.github/` — 协作机制

CI 只做三条轻量校验，**不做构建与部署**（架构书五(三)明确排除生产级 CI/CD）：

1. JSON 文件 Schema 校验
2. YAML 文件语法校验
3. 提交信息格式校验（commitlint）

## 四、命名约定

| 对象 | 规则 | 正例 | 反例 |
| --- | --- | --- | --- |
| 目录（通用） | kebab-case 小写 | `paper-deep-read` | `PaperDeepRead`、`paper_deep_read` |
| 规范文档 | `NN-标题.md`，NN 为两位序号 | `01-目录结构规范.md` | `目录结构.md` |
| ADR | `ADR-NNNN-标题.md` | `ADR-0001-采用GitHub主仓加Gitee镜像.md` | `adr1.md` |
| 迭代记录 | `YYYY-MM-DD-主题.md` | `2026-09-18-规范建立.md` | `log1.md` |
| 简报数据 | `briefing-YYYY-MM-DD.json` | `briefing-2026-09-18.json` | `briefing_today.json` |
| 提示词 | `<层次>-<对象>.md` | `task-前沿雷达.md` | `prompt3.md` |
| Skill 目录 | kebab-case | `briefing-generate` | `briefingGenerate` |
| Python 脚本 | snake_case | `export_briefing.py` | `exportBriefing.py` |

**禁止出现的文件**：`新建文本文档.txt`、`副本.md`、`test1.py`、`final_v2_真正最终版.md`。版本区分靠 Git，不靠文件名。

## 五、新增目录的判定流程

当需要一个新目录时，按顺序回答三个问题：

1. **它属于架构书四层中的哪一层？** —— 若无法归入任何一层，说明它可能属于被排除的选型（自建后端、重型前端等），应重新评估需求。
2. **它是否与已排除的选型相关？** —— 架构书五(三)排除项：重型前端框架、自建后端与数据库、Web 侧独立调大模型、微服务与容器编排、生产级监控与 CI/CD。相关则不新增。
3. **它能否放进已有目录的子目录？** —— 能则优先放子目录，保持顶层目录数量稳定。

三道问题都通过后，新增目录需在本文件 §2 目录树中同步更新，并在 PR 中说明理由。

## 六、目录结构检查清单

- [ ] 顶层目录与 §2 目录树一致，无计划外目录
- [ ] `knowledge/` 三库无混放，`domains/` 下知识单元均有 `source` 字段
- [ ] `prompts/` 四层目录齐全，文件命名符合 `<层次>-<对象>.md`
- [ ] `skills/` 下每个 Skill 目录均有含三节（输入契约/输出格式/失败处理）的 README
- [ ] `data/` 下无手工编辑痕迹，均由 `scripts/` 生成
- [ ] `web/` 无构建配置、无框架依赖、未调用大模型 API
- [ ] `iteration-log/` 无删除记录，命名符合日期格式
- [ ] 无 `副本`、`最终版`、`test1` 类命名
