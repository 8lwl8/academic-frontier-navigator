> 文档编号：SPEC-02
> 文档版本：V1.0
> 生效日期：2026-09-18
> 上游依据：架构书 五(一) 数据格式选型、六(一) 数据分类、六(二) 合规设计要点、四(二) Web 入口

## 一、三种格式的边界

架构书五(一)给出选型：**Markdown（知识单元）、JSON（结构化输出）、YAML（配置）**，并注明「纯文本优先，便于版本管理与平台解析」。这三者的边界必须一次性划清，否则团队会在「这个字段该写 md 还是 json」上反复消耗。

| 格式 | 唯一职责 | 判断标准 | 存放位置 |
| --- | --- | --- | --- |
| **Markdown** | 承载**人读的叙述性内容** | 内容需要被人类阅读理解、且需要说明理由 | `docs/`、`knowledge/`、`prompts/`、`iteration-log/` |
| **JSON** | 承载**机器读的结构化数据** | 内容要被程序或 Web 页面直接消费 | `data/`、`knowledge/intelligence/`、`skills/*/samples/` |
| **YAML** | 承载**配置** | 内容是「参数」而非「数据」，需要人经常手改 | `configs/` |

### 边界判定三问

遇到不确定时，依次问：

1. **它是给人看的还是给程序看的？** 人看 → Markdown；程序看 → JSON。
2. **它是「内容」还是「参数」？** 内容 → JSON/Markdown；参数（阈值、路径、开关） → YAML。
3. **它需要写理由吗？** 需要长篇解释「为什么」 → Markdown；只需要「是什么」 → JSON/YAML。

> **反面案例**：把学习路线的知识点依赖关系写成一段 Markdown 文字，让 Web 侧去正则解析 —— 这是错误用法。依赖关系是结构化数据，应为 JSON（见 §4.2）。**反之**，把「为什么这条路线这样安排」写成 JSON 的 `reason` 长字符串 —— 也是错误用法，理由属于叙述，应写 Markdown。

## 二、通用约定（三格式共享）

### 2.1 字符与编码

| 项 | 规定 |
| --- | --- |
| 编码 | UTF-8 **无 BOM** |
| 换行符 | LF（`\n`），由 `.editorconfig` 与 `.gitattributes` 双重保障 |
| 缩进 | Markdown / YAML 用 **2 空格**；JSON 用 **2 空格**；Python 用 **4 空格** |
| 行尾空格 | 一律去除 |
| 文件末尾 | 保留一个空行 |

### 2.2 命名风格

| 场景 | 风格 | 示例 |
| --- | --- | --- |
| JSON / YAML 字段名 | `lower_snake_case` | `paper_id`、`published_date` |
| 枚举值 | `lower_snake_case` | `high`、`in_progress` |
| 文件名 | kebab-case（见 SPEC-01 §4） | `briefing-2026-09-18.json` |
| 时间戳字段 | 后缀 `_at` | `created_at`、`verified_at` |
| 日期字段 | 后缀 `_date`，格式 `YYYY-MM-DD` | `published_date` |
| 布尔字段 | 前缀 `is_` / `has_` | `is_verified`、`has_fulltext` |

### 2.3 时间与时区

| 项 | 规定 |
| --- | --- |
| 纯日期 | `YYYY-MM-DD`，如 `2026-09-18` |
| 完整时间 | ISO 8601 带时区偏移，如 `2026-09-18T14:42:00+08:00` |
| 时区 | 统一 **UTC+8**（团队与赛事均在中国境内） |
| 禁用 | `2026/9/18`、`09-18-2026`、`Sep 18, 2026`、`昨天`、`刚刚` |

> 时间格式不统一是数据合并失败的首要原因。所有结构化数据中的时间字段**必须**满足上述格式，Schema 中以正则强制。

### 2.4 出处标注（合规硬性要求）

架构书六(2)要求「**出处标注**：所有学术内容附来源，便于用户核验」，四(2)要求 Web 侧「所有条目均标注出处链接」。这是**合规要求而非最佳实践**，因此在格式层面强制：

- Markdown 中的学术内容：文末必须有 `## 参考来源` 段落，逐条列出。
- JSON 中的学术内容：**必须**含 `source` 对象，且 `source.url` 为必填（Schema 强制）。

## 三、Markdown 约定

### 3.1 基础语法

| 项 | 规定 | 说明 |
| --- | --- | --- |
| 标题层级 | `#` 仅用于文档标题，且每文件仅一个；层级不跳级 | 从 `#` 到 `##` 到 `###`，不出现 `#` 直接到 `###` |
| 列表 | 无序用 `-`，有序用 `1.` `2.` | 不用 `*` 或 `+`，避免混用 |
| 强调 | 粗体 `**`，行内代码 `` ` `` | 少用斜体，中文斜体辨识度低 |
| 表格 | 必须有表头分隔行 | 表格前后各留一个空行 |
| 链接 | `[文字](URL)` | 不用裸 URL；URL 中的中文需编码 |
| 代码块 | 必须标注语言 | 如 ```` ```bash ````、```` ```json ```` |
| 引用 | `>` | 用于定义、外部条款引用、注意事项 |
| 分隔线 | `---` | 仅用于大章节之间，谨慎使用 |

### 3.2 知识单元 Markdown 规范（关键）

`knowledge/domains/` 下的知识单元采用**带 YAML front matter 的 Markdown**。这是 Markdown 与 YAML 唯一的交叉区，格式固定：

```markdown
---
id: kn-0001
title: 对比学习中的 InfoNCE 损失
domain: 机器学习
sub_domain: 自监督学习
knowledge_point: 对比学习
level: 经典
tags: [对比学习, 自监督, 损失函数]
source:
  type: paper
  title: Representation Learning with Contrastive Predictive Coding
  authors: [Aaron van den Oord, Yazhe Li, Oriol Vinyals]
  url: https://arxiv.org/abs/1807.03748
  published_date: 2018-07-10
prerequisites: [kn-0003]
created_at: 2026-09-18
updated_at: 2026-09-18
---

## 一句话概括

用噪声对比估计把「预测未来表征」转化为可优化的分类问题。

## 核心内容

（正文……）

## 与学习路线的关联

前置知识点：`kn-0003`（互信息基础）

## 参考来源

1. van den Oord et al. *Representation Learning with Contrastive Predictive Coding*. arXiv:1807.03748, 2018. <https://arxiv.org/abs/1807.03748>
```

**front matter 字段约束**：

| 字段 | 必填 | 类型 | 约束 |
| --- | --- | --- | --- |
| `id` | ✅ | string | `kn-` + 四位数字，**全库唯一** |
| `title` | ✅ | string | 不超过 60 字 |
| `domain` | ✅ | string | 领域名 |
| `sub_domain` | ✅ | string | 子方向 |
| `knowledge_point` | ✅ | string | 知识点，用于建依赖关系 |
| `level` | ✅ | enum | `入门` / `经典` / `前沿` |
| `tags` | ❌ | array | 建议 3~6 个 |
| `source` | ✅ | object | **合规硬性要求**，见下表 |
| `prerequisites` | ❌ | array | 前置知识点 `id` 列表，构成架构书三(4)的依赖结构 |
| `created_at` | ✅ | date | `YYYY-MM-DD` |
| `updated_at` | ✅ | date | `YYYY-MM-DD`，内容变更时同步更新 |

**`source` 对象**（对应架构书六(1)「领域公开知识」类，敏感级别：低）：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `type` | ✅ | enum：`paper` / `textbook` / `survey` / `course` / `repo` / `doc` |
| `title` | ✅ | 原始标题（保留原语言，不翻译） |
| `authors` | ❌ | 作者数组 |
| `url` | ✅ | **可公开访问**的链接，对应语料准入标准 |
| `published_date` | ❌ | `YYYY-MM-DD` |

> **`prerequisites` 是本项目的架构亮点，也是 Web 路线图的直接数据来源。** 架构书三(4)指出「该依赖结构是学习路线生成的依据，也是本项目知识库设计相比普通文档库的核心差异」，八章更把它列为「技术创新性」的支撑点。填写时务必准确，**不得出现循环依赖**（A 依赖 B 且 B 依赖 A）。

### 3.3 迭代记录 Markdown 规范

`iteration-log/` 下的文件采用统一结构，模板见 `templates/iteration-log.template.md`。核心要求：

- 每轮对话/迭代**一份文件**，记录时间、参与人、AI 工具、目的；
- **必须包含原始提示词与 AI 关键回复的摘录** —— 这是评审「AI 工具使用深度」（25%）的直接证据；
- 人工修改说明：AI 输出不能直接用，**必须记录人工做了哪些调整、为什么调整**。这一点对应 SPEC-04 的「AI 用于提效而非替代」。

### 3.4 提示词 Markdown 规范

`prompts/` 下的文件头部使用固定信息块（这里用 YAML 承载元信息，正文用 Markdown）：

```markdown
---
prompt_id: task-frontier-radar
layer: task
target_agent: 前沿雷达智能体
version: V1.2
status: verified
platform_validated_at: 2026-09-20
draft_location: local
---

## 用途

生成领域每日简报，按相关性分层输出。

## 提示词正文

（可直接粘贴到平台的提示词内容）

## 迭代说明

| 版本 | 日期 | 变更 | 验证结果 |
| --- | --- | --- | --- |
| V1.0 | 2026-09-18 | 初稿 | 未验证 |
| V1.2 | 2026-09-20 | 增加相关性分层要求 | 平台验证通过 |
```

`status` 取值：`draft`（本地起草）/ `testing`（平台验证中）/ `verified`（验证通过）/ `deprecated`（废弃）。

> 这套字段直接落实架构书二(4)的「**本地起草 → 平台验证 → 版本留痕**」流程：`draft_location` 记录起草来源，`platform_validated_at` 记录平台验证时间，`迭代说明` 表格承担版本留痕。

## 四、JSON 约定

### 4.1 基础语法

| 项 | 规定 |
| --- | --- |
| 缩进 | 2 空格 |
| 引号 | 双引号，键名与字符串值均用双引号 |
| 尾随逗号 | **禁止**（JSON 标准不允许） |
| 注释 | **禁止**（JSON 标准不支持，需注释请用 YAML 或独立 README） |
| 空值 | 用 `null`，**不用**空字符串 `""` 表示「无」 |
| 空数组/对象 | 用 `[]` / `{}`，不用 `null` 表示「空集合」 |
| 文件体积 | 单个文件不超过 1 MB；超出则分片（如简报按月分片） |
| 校验 | 每个 JSON 类型**必须**有对应 Schema 于 `schemas/` |

### 4.2 核心数据结构：学习路线（`data/route/`）

对应 Web「学习路线」页 —— 架构书四(2)要求「路线图采用有向图形式表达知识点依赖顺序」。

```json
{
  "schema_version": "1.0",
  "route_id": "route-cv-2026-09-18",
  "topic": "计算机视觉",
  "generated_at": "2026-09-18T14:42:00+08:00",
  "generated_by": "route-generate@v1.0",
  "user_profile_ref": "profile-anon-0001",
  "stages": [
    {
      "stage_id": "stage-01",
      "name": "前置基础",
      "order": 1,
      "estimated_weeks": 2,
      "knowledge_points": [
        {
          "kp_id": "kn-0003",
          "name": "线性代数基础",
          "level": "入门",
          "status": "completed",
          "prerequisites": [],
          "source": {
            "type": "textbook",
            "title": "Linear Algebra and Its Applications",
            "url": "https://example.org/ref"
          }
        }
      ]
    }
  ],
  "edges": [
    { "from": "kn-0003", "to": "kn-0001", "relation": "prerequisite_of" }
  ]
}
```

**关键设计说明**：

- `edges` 数组显式表达知识点依赖的有向边 —— 这是 Web 侧用 ECharts 画有向图的直接输入，避免了「前端从 stages 嵌套结构里猜依赖关系」。
- `generated_by` 记录生成来源（Skill 名 + 版本），保证数据可溯源。
- 所有知识点**必须**带 `source`，落实架构书四(2)「所有条目均标注出处链接」。

### 4.3 核心数据结构：每日简报（`data/briefing/`）

对应 Web「前沿简报」页 —— 架构书四(2)要求「简报采用按相关性分层的列表，高相关内容优先展示」。

```json
{
  "schema_version": "1.0",
  "briefing_date": "2026-09-18",
  "keywords": ["多模态", "视觉语言模型"],
  "time_window": { "from": "2026-09-11", "to": "2026-09-18" },
  "generated_at": "2026-09-18T08:00:00+08:00",
  "items": [
    {
      "paper_id": "arxiv-2509.01234",
      "title": "…",
      "authors": ["…"],
      "published_date": "2026-09-16",
      "relevance": "high",
      "relevance_reason": "与用户关注方向「多模态对齐」高度相关",
      "quick_read": "一句话中文速读……",
      "pdf_url": "https://arxiv.org/pdf/2509.01234",
      "source": {
        "type": "paper",
        "title": "…",
        "url": "https://arxiv.org/abs/2509.01234"
      }
    }
  ],
  "stats": { "total_fetched": 42, "total_included": 5, "high_relevance": 2 }
}
```

**`relevance` 枚举**：`high` / `medium` / `low` —— 与架构书四(2)「按相关性分层」对应。

> **幂等性要求**：架构书三(2)规定定时任务「同一天重复触发不应产生重复简报」。因此文件名固定为 `briefing-YYYY-MM-DD.json`，**同日重复生成直接覆盖**该文件，不产生 `briefing-2026-09-18-2.json` 这类文件。

### 4.4 核心数据结构：知识资产（`data/assets/`）

```json
{
  "schema_version": "1.0",
  "asset_id": "asset-0001",
  "type": "note",
  "title": "…",
  "summary": "…",
  "tags": ["…"],
  "origin": {
    "kind": "conversation",
    "ref": "session-2026-09-18-01",
    "extracted_by": "asset-extract@v1.0"
  },
  "visibility": "private",
  "created_at": "2026-09-18",
  "updated_at": "2026-09-18"
}
```

**`visibility` 枚举**：`private` / `campus` / `public` —— 严格对应架构书六(1)「个人知识资产」的访问控制（用户自主控制可见度：私密 / 校内 / 公开），**默认 `private`**，与架构书六(2)「**默认私密**」一致。

### 4.5 JSON 通用字段规范

所有 JSON 数据文件**必须**包含以下顶层字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema_version` | ✅ | 随 Schema 破坏性变更递增，如 `"1.0"` → `"2.0"` |
| `generated_at` | ✅ | ISO 8601 带时区 |
| `generated_by` | 建议 | `<skill-name>@v<version>`，用于溯源 |

## 五、YAML 约定

### 5.1 基础语法

| 项 | 规定 | 理由 |
| --- | --- | --- |
| 缩进 | 2 空格，**禁止 Tab** | Tab 是 YAML 解析错误的头号原因 |
| 文档起始 | 可省略 `---`，多文档时必须加 | 保持简洁 |
| 字符串引号 | 默认不加；含特殊字符（`:` `#` 开头数字）时用双引号 | 减少视觉噪音 |
| 布尔值 | `true` / `false`（小写） | 避免 YAML 1.1 的 `yes`/`no` 歧义 |
| 空值 | `null` | 不用 `~` |
| 数组 | 短数组用流式 `[a, b]`，长数组用块式 | 兼顾可读性与 diff 友好 |
| 注释 | `#` 前留一个空格，注释解释「为什么」而非「是什么」 | 与代码注释原则一致 |

### 5.2 主配置文件（`configs/afn.config.yaml`）

这是本仓库唯一的运行配置入口，承载架构书三(2)定时任务的可配置项：

```yaml
# AFN 主配置
# 依据：架构书 三(二) 定时任务设计

config_version: "1.0"
updated_at: "2026-09-18"

# ---- 前沿动态每日追踪（架构书 三(二)）----
frontier_radar:
  # 触发策略：按固定周期触发，避免高频触发消耗算力
  schedule:
    enabled: true
    cron: "0 8 * * *"          # 每日 08:00（UTC+8）
    timezone: "Asia/Shanghai"
  # 任务范围：可配置关注的关键词集合、论文来源、时间窗口
  scope:
    keywords: ["多模态", "视觉语言模型", "具身智能"]
    sources: ["arxiv"]
    lookback_days: 7
  # 产出形态：结构化简报 + 对话内推送
  output:
    formats: [json, dialogue]
    data_path: "data/briefing"
  # 幂等性：同一天重复触发不应产生重复简报
  idempotent: true
  # 失败处理：抓取失败时降级并记录，不阻塞用户其他操作
  on_failure:
    strategy: degrade
    message: "本次暂无可更新内容"
    log_path: "logs/radar-failure.log"

# ---- 相关性分层（架构书 四(二)）----
relevance:
  levels: [high, medium, low]
  default_level: medium
  # 高相关内容优先展示
  display_order: [high, medium, low]

# ---- 知识库（架构书 三(四)）----
knowledge_base:
  domains_path: "knowledge/domains"
  intelligence_path: "knowledge/intelligence"
  personal_path: "knowledge/personal"
  # 语料准入标准：来源可公开访问、有明确作者与出处
  ingestion:
    require_source_url: true
    require_public_access: true
    reject_unknown_origin: true

# ---- 合规（架构书 六(二)）----
compliance:
  # 知识边界声明：超出范围必须显式声明，不得推测作答
  knowledge_boundary_declaration: true
  # 出处标注：所有学术内容必须附来源
  require_citation: true
  # 可见度控制：默认私密
  default_visibility: private
  # AI 使用边界：保留完整迭代记录
  ai_iteration_log_required: true
```

### 5.3 YAML 禁止项

| 禁止 | 原因 |
| --- | --- |
| 锚点与别名（`&` / `*`） | 可读性差，评审难以理解 |
| 复杂嵌套超过 4 层 | 结构应简化或拆文件 |
| 多文档（`---` 分隔多个根） | 除特殊场景外不用 |
| 在配置中硬编码密钥 | 密钥走环境变量，见 §7 |
| Tab 缩进 | 解析失败 |

## 六、格式转换链

数据在系统中遵循单向流动，**禁止逆向手工编辑**：

```text
原始语料（论文/教材/课程）
    ↓ 人工提炼 + AI 辅助
knowledge/domains/*.md          （Markdown 知识单元，带 front matter）
    ↓ scripts/ 脚本导出
data/route|briefing|assets/*.json （结构化 JSON，Schema 校验）
    ↓ 只读加载
web/                             （HTML + 原生 JS + ECharts 渲染）
```

> **规则**：任一环节的数据变更，**必须从上游重新生成**，不得直接改下游文件。理由：下游文件丢失了溯源信息（`generated_by`），手工编辑后无法回答评审「这个数据怎么来的」。

## 七、数据分类与可见度（合规）

严格对应架构书六(1)的数据分类表：

| 数据类型 | 敏感级别 | 存储位置 | 访问控制 | 仓库内如何处理 |
| --- | --- | --- | --- | --- |
| 领域公开知识 | 低 | `knowledge/domains/` | 公开 | ✅ 正常提交 |
| 动态情报 | 低 | `knowledge/intelligence/` | 公开 | ✅ 正常提交 |
| 用户画像与学习轨迹 | 中 | `knowledge/personal/` | 仅用户本人及授权范围 | ⚠️ **真实数据不入库**，仅提交脱敏样例 |
| 个人知识资产 | 中 | `knowledge/personal/` | 用户自主控制（私密/校内/公开），**默认私密** | ⚠️ **真实数据不入库**，仅提交脱敏样例 |

### 敏感文件处理规则

1. 真实个人数据文件命名加后缀 `.private.md` / `.private.json`，已在 `.gitignore` 屏蔽。
2. 仓库内只保留 `*.example.md` / `*.example.json` 形式的脱敏样例。
3. 若误提交敏感文件，**必须**立即执行：`git rm --cached <file>` → 补进 `.gitignore` → 提交，并在 `iteration-log/` 记录这次事故与补救措施。

## 八、密钥管理

**任何形式的密钥、Token、API Key 均不得出现在仓库中。**

| 项 | 规定 |
| --- | --- |
| 存放位置 | 环境变量（本地 `.env`，已被 `.gitignore` 屏蔽） |
| 仓库内提供 | `.env.example`，仅含键名与说明，值为占位符 |
| 配置文件引用 | YAML 中写 `${ENV_VAR_NAME}`，不写真实值 |
| 校验 | CI 中对 `configs/` 执行正则扫描，命中疑似密钥则失败 |
| 泄露处置 | 立即吊销该密钥（**改代码无用，密钥已进 Git 历史**）并在 `iteration-log/` 记录 |

> 架构书五(一)已说明智能体能力全部由 LearnBuddy 平台承载，**Web 侧不独立调用大模型 API**，因此本项目理论上不需要在仓库中存放任何模型密钥。若出现「需要往仓库放 API Key」的需求，先回头确认是否违背了架构书五(3)的排除项。

## 九、格式检查清单

### Markdown

- [ ] 文件顶部有 YAML front matter（知识单元、提示词）且字段类型正确
- [ ] 代码块标注了语言
- [ ] 表格有表头分隔行，前后有空行
- [ ] 学术内容文末有「参考来源」段落
- [ ] 标题层级不跳级，`#` 每文件仅一个

### JSON

- [ ] 2 空格缩进，UTF-8 无 BOM
- [ ] 无尾随逗号、无注释
- [ ] 含 `schema_version`、`generated_at`、`generated_by`
- [ ] 学术条目含 `source.url`
- [ ] 通过 `schemas/` 中对应 Schema 校验
- [ ] 空值用 `null`，空集合用 `[]` / `{}`

### YAML

- [ ] 2 空格缩进，无 Tab
- [ ] 布尔值小写 `true` / `false`
- [ ] 无锚点别名、无多文档
- [ ] 无硬编码密钥（用 `${ENV_VAR}`）
- [ ] `configs/afn.config.yaml` 通过语法校验

### 通用

- [ ] 字段名为 `lower_snake_case`
- [ ] 时间格式符合 ISO 8601 / `YYYY-MM-DD`
- [ ] 无敏感数据进入仓库
- [ ] 文件末尾保留一个空行、LF 换行
