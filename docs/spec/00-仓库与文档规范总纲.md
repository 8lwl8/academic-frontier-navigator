## 一、这份规范解决什么问题

AFN 是一个 **10 天交付周期**的参赛作品，团队在其上并行推进知识库、Skills、提示词与 Web 展示四条工作线。周期短、并行度高，最容易发生的失控点不是技术难题，而是：

- 同一份内容被两个人改出两个版本，无法判断哪个是最新；
- 评审要看「AI 使用深度」，但对话记录散落在各人设备里，事后无法还原；
- 知识单元与 Web 数据的字段各写各的，Web 侧拿到 JSON 还要人肉对齐字段名；
- 出问题时无法定位「当时为什么这么改」。

因此本规范只做一件事：**让所有产出物在格式上是可预测的，在时间上是可追溯的。** 它由三根支柱构成 —— **统一的目录结构**（东西放哪里）、**统一的格式约定**（东西长什么样）、**统一的留痕机制**（东西怎么来的）。

### 设计原则

| 原则 | 含义 | 在规范中的体现 |
| --- | --- | --- |
| **纯文本优先** | 所有需要版本管理的内容以纯文本承载 | 知识单元用 Markdown、结构化输出用 JSON、配置用 YAML |
| **单一事实来源** | 同一事实只在一处定义，其余引用 | 规范条款有唯一编号；术语表集中在 SPEC-02 附录 |
| **留痕优先于整洁** | 宁可保留过程记录，也不为了好看删掉迭代痕迹 | `iteration-log/` 只增不删；ADR 不覆盖旧决策 |
| **约定优于配置** | 默认路径与默认字段名固定，减少沟通成本 | 目录结构固定；JSON/YAML 字段采用 lower_snake_case |
| **工具可校验** | 能自动检查的就不靠人盯 | JSON Schema、commitlint、pre-commit、CI |

## 三、与架构书的对应关系

本规范不是独立发明，而是把架构书中已有的技术选型**收敛为可执行的工程约定**。

| 架构书条款 | 架构书给出的选型 | 本规范的落地动作 |
| --- | --- | --- |
| 五(一) 平台侧 · 编程语言 | Python | 自研 Skills 与本地脚本统一 Python 3.10+，落 `skills/`、`scripts/` |
| 五(一) 平台侧 · 数据格式 | Markdown（知识单元）、JSON（结构化输出）、YAML（配置） | 三者边界在 SPEC-02 中逐条界定，并配 JSON Schema |
| 五(一) 平台侧 · 版本管理 | Git + GitHub / Gitee | 采用 GitHub 主仓 + Gitee 镜像，流程见 SPEC-03 |
| 五(一) Skills 开发 | 按 LearnBuddy Skills 规范，保持可移植性 | `skills/` 内每个组件独立目录，含输入契约与输出格式 |
| 五(二) Web 侧 | HTML + CSS + 原生 JS + ECharts，静态 JSON，无构建工具 | `web/` 目录结构固定，数据只读消费 `data/` |
| 五(三) 明确排除的选型 | 重型前端框架、自建后端、Web 侧独立调大模型、微服务、生产级 CI/CD | 目录结构中**不预留**这些位置，避免误入 |
| 六(一) 数据分类 | 领域公开知识 / 用户画像与学习轨迹 / 个人知识资产 | 对应 `knowledge/` 三个子库，权限约定见 SPEC-02 §7 |
| 六(二) 合规设计要点 | 知识边界声明、出处标注、可见度控制、知识产权、**AI 使用边界（手册 8.3）** | 整份 SPEC-04 专述；出处标注要求写入 JSON Schema 必填字段 |
| 二(四) 提示词工程策略 | **本地起草 → 平台验证 → 版本留痕** | 该流程即 `prompts/` + `iteration-log/` 的设计依据，见 SPEC-03 §6 |

> **关键取舍说明**：架构书五(三)明确排除了「生产级监控、CI/CD 流水线」。因此本仓库的 CI **只做三条轻量校验**（格式、Schema、提交信息），**不构建、不部署、不做生产化建设**。这一点在 SPEC-03 §7 有明确边界，请勿自行加码。

## 四、四级可用性：规范如何不变成摆设

规范写完没人执行是常态。为此本规范设计了四道防线，强度递增：

| 级别 | 机制 | 触发时机 | 违反后果 | 落地位置 |
| --- | --- | --- | --- | --- |
| **L1 约定** | 目录结构与命名约定 | 新建文件时 | 无强制，靠评审指出 | SPEC-01 |
| **L2 编辑器** | EditorConfig + pre-commit 钩子 | 本地 commit 前 | 钩子拦截，需修正才能提交 | `configs/.pre-commit-config.yaml` |
| **L3 校验** | JSON Schema + commitlint | 提交时 / CI | 校验失败阻止合并 | `schemas/`、`configs/commitlint.config.js` |
| **L4 评审** | PR 模板 + CODEOWNERS | 合并前 | 无人批准不可合并 | `.github/` |

> **务实提醒**：10 天周期下，L1 与 L4 是主力，L2 与 L3 按需启用。若启用钩子拖慢了迭代节奏，可以临时 `git commit --no-verify` 绕过，但**必须在 `iteration-log/` 中记录这次绕过的原因**。规范服务于交付，不是反过来。

## 五、角色与职责

团队规模小，职责不宜过细，按「谁碰哪类文件谁负责」划分。

| 角色 | 负责范围 | 对应目录 | 关键职责 |
| --- | --- | --- | --- |
| **知识库负责人** | 领域知识库建设与语料准入 | `knowledge/domains/` | 保证语料满足架构书三(四)的准入标准；维护知识点依赖关系 |
| **能力层负责人** | 自研 Skills 与定时任务 | `skills/`、`configs/afn.config.yaml` | 每个 Skill 有明确输入契约、输出格式与失败处理 |
| **提示词负责人** | 分层提示词的起草与迭代 | `prompts/` | 严格执行「本地起草 → 平台验证 → 版本留痕」 |
| **Web 负责人** | 只读展示层 | `web/`、`data/` | 只消费 `data/` 中的静态 JSON，不实现独立智能体逻辑 |
| **文档与留痕** | 规范维护、迭代记录归档 | `docs/`、`iteration-log/` | 每轮迭代结束 24h 内归档记录；审核 AI 使用留痕完整性 |
| **队长** | 统稿、评审对接、最终提交 | 全仓库 | 合并决策、版本发布、作品上传 |

> 架构书二(一)明确主控智能体「不做可视化渲染」，四(二)明确 Web 入口「不实现独立的智能体逻辑」。这两个边界在人员分工上同样成立：**Web 负责人不碰提示词，提示词负责人不碰 Web 渲染逻辑。**

## 六、落地检查清单

### 首次建仓

- [ ] 按 SPEC-05 完成 `git init`、初始提交、远端绑定
- [ ] 确认仓库为 **Public**，根目录含 `LICENSE`（MIT）
- [ ] 确认 `.gitignore` 已屏蔽密钥与个人数据文件
- [ ] 全体成员完成 `git config user.name` / `user.email` 设置

### 每次提交前

- [ ] 提交信息符合 Conventional Commits（见 SPEC-03 §4）
- [ ] 新增的 JSON 文件通过对应 Schema 校验
- [ ] 若本轮使用了 AI 生成内容，已在 `iteration-log/` 留下记录

### 每次迭代结束

- [ ] `iteration-log/YYYY-MM-DD-*.md` 已归档
- [ ] `CHANGELOG.md` 的 `[Unreleased]` 段落已更新
- [ ] 若产生架构级取舍，已在 `docs/decisions/` 新增 ADR

### 提交作品前

- [ ] 全部 `iteration-log/` 完整，可还原 AI 使用过程（对应评审 25% 分值）
- [ ] `README.md` 中的在线访问链接真实可用
- [ ] 第三方资源授权已在 SPEC-04 §5 记录
