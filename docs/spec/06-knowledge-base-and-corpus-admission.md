## 一、这份规范解决什么问题

架构书三(四)已经给出知识库的**结论**：分三个库，按「领域 → 子方向 → 知识点 → 文献」组织，并标注知识点之间的依赖关系。但结论不足以支撑施工 —— 团队真正会卡住的是下面这些问题：

| 会卡住的问题 | 本规范在哪答 |
| --- | --- |
| 一篇论文到底该进`domains/`还是`intelligence/`？ | §三 三分库判据 |
| 「领域 → 子方向 → 知识点 → 文献」四层，每一层的边界在哪、谁归谁？ | §四 四层组织模型 |
| 知识点依赖关系怎么建模？谁依赖谁由谁说了算？ | §五 依赖关系模型 |
| 什么语料能入库、什么不能？谁来判断、按什么标准？ | §六 语料准入标准 |
| 已经入库的语料后来不合格了怎么办？ | §七 复核与退出机制 |
| 知识库是给智能体用的，怎么保证它检索到的不是噪声？ | §八 检索口径约定 |

> **一句话定位**：SPEC-02 定义了知识单元**长什么样**，本规范定义知识库里**有什么、怎么组织、什么能进来**。

### 与架构书的关系：落实而非新增

本规范不引入架构书之外的任何新概念。逐条对应如下。

| 架构书条款 | 架构书原文结论 | 本规范的落地动作 |

## 二、知识库在系统中的位置

### 2.1 三库与智能体的对应关系

架构书三(四)已明确三库的「服务对象」。这是后续所有设计决策的第一依据 —— **判断一条语料属于哪个库，先问它服务哪个智能体**。

| 子库 | 目录 | 服务对象（架构书原文） | 由哪个智能体主要消费 | 由哪个 Skill 写入 |
| --- | --- | --- | --- | --- |
| **领域知识库** | `knowledge/domains/` | 路线规划、论文精读 | 路线规划智能体、主控智能体 | 人工提炼（`paper-deep-read` 辅助） |
| **动态情报库** | `knowledge/intelligence/` | 前沿雷达 | 前沿雷达智能体 | `briefing-generate` |
| **个人资产库** | `knowledge/personal/` | 知识管家 | 知识管家智能体 | `asset-extract` |

> **三库不得混放**（SPEC-01 §3）。混放的典型后果是：把某天抓到的论文摘要直接写进 `domains/`，导致「领域知识库」混入未经验证的时效性内容，路线规划智能体据此生成的学习路线把一篇刚出的、尚未被领域消化的论文当作必读经典。**这是本项目最需要防的一类错误。**

### 2.2 数据分类与提交策略

严格对应架构书六(1)的数据分类表与 SPEC-02 §7：

| 子库 | 数据敏感级别 | 可见度 | 仓库提交策略 |
| --- | --- | --- | --- |
| `domains/` | 低 | 公开 | ✅ 正常提交 |
| `intelligence/` | 低 | 公开 | ✅ 正常提交（只提交结构化简报，不提交原始抓取流水） |
| `personal/` | 中 | 用户自主控制，**默认私密** | ⚠️ **只提交 `*.example.md` 脱敏样例**，真实数据不入库 |

`personal/` 的脱敏要求见 §六(四)。

### 2.3 三库的关系：不是三个抽屉，是一条流水线

把三库理解成互不相干的三个文件夹，是设计上最容易犯的错。它们实际构成架构书一(三)「情报闭环」与「资产闭环」的载体：

```text
              ┌──────────────────────┐
              │  domains/  领域知识库 │  ← 稳定层：学科的结构化知识骨架
              │  （经典、奠基、体系化）│     变化慢，是路线生成的地基
              └───────────┬──────────┘
                          │ 提供概念与判断依据
                          ↓
              ┌──────────────────────┐
              │ intelligence/ 动态情报 │  ← 增量层：每日新增的动态
              │  （时效、高相关、待筛选）│     变化快，是雷达的产出
              └───────────┬──────────┘
                          │ 用户筛选后精读、对话、提炼
                          ↓
              ┌──────────────────────┐
              │  personal/  个人资产库 │  ← 沉淀层：用户自己的理解
              │  （笔记、结论、轨迹）  │     归属个人，默认私密
              └──────────────────────┘
```

**关键规则：三库之间的流动是单向的，且必须经过「人工/智能体提炼」这一道工序，不得直接复制。**

| 流动 | 允许 | 不允许 |
| --- | --- | --- |
| 情报 → 领域 | ✅ 某篇论文经时间检验被确认为代表性成果后，**重新提炼**为知识单元入库 | ❌ 把情报条目直接复制进 `domains/` |
| 情报 → 个人 | ✅ 用户精读后形成笔记，沉淀为个人资产 | ❌ 把整个简报原样存为个人资产 |
| 领域 → 个人 | ✅ 知识点学习后产生的理解与总结 | ❌ 把知识单元原文复制为个人笔记 |
| 个人 → 领域 | ⚠️ 原则上不可。个人资产若确有领域公共价值，须经知识库负责人**重新提炼并补全 source** 后另行入库 | ❌ 直接把个人笔记提升为领域知识单元 |

> **「重新提炼」的含义**：目标库要求的字段、深度与出处完整度必须全部满足。跨库不是搬运，是**再加工**。

## 三、三分库判据

### 3.1 通用判据：三问定位

一条语料进来，依次问三个问题，任一问题得到明确答案即停止：

1. **它描述的是「这个领域公认的知识」，还是「最近发生的事」？**
   → 公认知识走 `domains/`；最近发生的事走 `intelligence/` 或 `personal/`。

2. **它的价值归属于「所有人」还是「某个用户」？**
   → 所有人走 `domains/` / `intelligence/`；某个用户走 `personal/`。

3. **它是「原材料」还是「加工产物」？**
   → 原材料（论文原文、教材章节、课程材料）进 `domains/`；加工产物按加工者归属：智能体加工的进 `intelligence/`，用户加工的进 `personal/`。

### 3.2 领域知识库 `domains/`

| 项 | 内容 |
| --- | --- |
| **定位** | 学科的结构化知识骨架，全部智能体能力的共同地基（架构书三(四)） |
| **内容来源（架构书原文）** | 顶会论文、经典教材、综述文章、公开课材料、开源项目文档 |
| **时间特征** | 稳定。一条知识单元的有效期以**年**计 |
| **粒度** | 一个知识单元 = **一个知识点**，而非一篇论文 |
| **格式** | Markdown + YAML front matter（SPEC-02 §3.2） |
| **数量级预期** | 初赛阶段聚焦单一细分方向，**30–60 条**为合理区间 |

**核心判据**：这条内容，**三年后是否仍然成立**？

- 成立 → `domains/`
- 不成立或需要大幅修正 → 它属于 `intelligence/`，或暂不入库

> **边界澄清**：一篇 2017 年的 Transformer 论文要进 `domains/`，**理由不是「它是 2017 年的」**，而是「它提出的自注意力机制已成为领域公认基础」。反之，2026 年 9 月刚放出的某篇新论文不应因为「作者是大牛」而进 `domains/` —— 它还没有经过时间检验，应留在 `intelligence/`。

**反例（不该进 `domains/`）**：

| 反例 | 为什么不该进 | 应去哪 |
| --- | --- | --- |
| 「arXiv 今日新论文 12 篇速览」 | 时效性内容，明天就过时 | `intelligence/` |
| 「我读 Attention 论文的笔记」 | 加工者是用户，价值归属个人 | `personal/` |
| 「某公众号对 GPT-4 的解读」 | 来源非原始、作者不明 | 不入库 |
| 「某模型在某个私有榜单上的分数」 | 无法公开核验 | 不入库 |
| 一整篇论文的全文搬运（无提炼） | 粒度错误，且违反版权 | 不入库（只提炼知识点） |

### 3.3 动态情报库 `intelligence/`

| 项 | 内容 |
| --- | --- |
| **定位** | 每日抓取的领域动态，供用户筛选后决定是否精读（架构书三(四)） |
| **内容来源（架构书原文）** | 每日抓取的论文与项目动态 |
| **时间特征** | 时效。单条情报的「保鲜期」为 `frontier_radar.scope.lookback_days`（默认 7 天） |
| **粒度** | 一次抓取产出一份**简报**，一份简报含多条**条目** |
| **格式** | JSON（结构化简报），Schema 为 `schemas/briefing.schema.json`；亦可存 Markdown 形式的说明性条目 |
| **数量级预期** | 每日一份，每份 3–10 条入选条目 |

**核心判据**：这条内容，**是否与本用户当前研究方向相关，且是「新增的」**？

- 是 → `intelligence/`
- 否 → 不入选（架构书四(2)要求「按相关性分层」，低相关的内容应当被过滤而非入库）

**与 `domains/` 的判定对照**：

| 场景 | 归属 | 理由 |
| --- | --- | --- |
| 2026-09 新发布的某篇多模态对齐论文，相关性 high | `intelligence/` | 有效期以周计 |
| 该论文提出的对齐损失函数，已成为子方向公认方法 | `domains/`（**另行提炼**） | 已通过时间检验 |
| 同一条内容同时出现在两处 | 不允许 | 重复会导致检索结果冗余 |

> **幂等性要求**：架构书三(2)规定定时任务「同一天重复触发不应产生重复简报」。因此简报文件名固定为 `briefing-YYYY-MM-DD.json`，**同日重复生成直接覆盖**，不产生 `briefing-2026-09-18-2.json` 这类文件。这条已写入 SPEC-02 §4.3。

### 3.4 个人资产库 `personal/`

| 项 | 内容 |
| --- | --- |
| **定位** | 用户自己的理解与轨迹，支撑知识管家智能体的检索、复用与导出（架构书三(四)） |
| **内容来源（架构书原文）** | 用户阅读笔记、对话结论、学习轨迹 |
| **时间特征** | 持续累积，随用户成长而增值 |
| **粒度** | 一条资产 = 一条可独立复用的结构化条目 |
| **格式** | Markdown（正文，`content_path` 指向）+ JSON（资产元数据，`data/assets/`） |
| **可见度** | `private`（默认）/ `campus` / `public`，对应架构书六(1) |

**核心判据（架构书三(三)）**：「只沉淀有长期价值的结构化信息，不记录原始对话流水」。

| 沉淀（✅） | 不沉淀（❌） |
| --- | --- |
| 「对比学习两种损失函数的适用边界与选择依据」——结构化结论 | 一次 30 轮的完整对话记录 |
| 「本阶段已完成的 3 个知识点与 2 个卡点」——进度结构化 | 「用户今天问了什么」的流水账 |
| 「该用户偏好先看代码再看公式」——偏好结构化 | 每次交互的原始文本 |
| 文献卡片（研究问题/方法/创新点/局限） | 论文全文 |

> **为什么强调「不记录原始对话流水」**：原始记录由对话历史承担（架构书三(三)）。若把流水也写进个人资产库，会导致检索时大量噪声命中，反而降低知识管家智能体的输出质量。**记忆的价值来自筛选，不来自堆积。**

### 3.5 三分库判据速查表

| 语料 | 归属 | 主要依据 |
| --- | --- | --- |
| Vaswani 等 2017 年提出 Transformer 的自注意力机制 | `domains/` | 公认基础，三年后仍成立 |
| 2026-09-17 arXiv 新出的某篇多模态论文 | `intelligence/` | 时效，未经时间检验 |
| 用户对某篇论文的批判性思考笔记 | `personal/` | 加工者为用户 |
| PyTorch 官方文档中关于 `nn.MultiheadAttention` 的条目 | `domains/` | 开源项目文档，稳定 |
| 智能体今天抓取到的一批论文清单 | `intelligence/` | 抓取产物 |
| 用户当前学习进度与卡点 | `personal/` | 学习轨迹 |
| 某篇 2020 年的论文，其方法已被后续工作普遍超越 | 视情况 | 若仍具方法论价值 → `domains/`（标注局限）；否则不入库 |

## 四、四层组织模型

架构书三(四)规定：「按『领域 → 子方向 → 知识点 → 文献』的层级组织」。

这四层不是四个文件夹，而是**同一条知识单元上的四个坐标** —— 一条 `domains/` 知识单元的 front matter 里，`domain` / `sub_domain` / `knowledge_point` 三个字段正好承载前三层，`source` 承载第四层。

### 4.1 四层的定义与字段映射

| 层级 | 定义 | 数量级 | front matter 字段 | 约束 |
| --- | --- | --- | --- | --- |
| **L1 领域 (domain)** | 学科顶层方向 | 全库 **1–2 个** | `domain` | 必须收敛到单一细分方向（风险应对：「宁可窄而深，不做宽而浅」） |
| **L2 子方向 (sub_domain)** | 领域内的技术分支 | 每个领域 **3–6 个** | `sub_domain` | 子方向之间应尽量正交，避免重叠归类 |
| **L3 知识点 (knowledge_point)** | 可独立学习的知识单元 | 每个子方向 **3–10 个** | `knowledge_point` + `id` | **一条知识单元 = 一个知识点**，`id` 全库唯一 |
| **L4 文献 (literature)** | 知识点的支撑材料 | 每条知识点 **1–n 篇** | `source`（含 `url` 必填） | 必须可公开访问；`url` 由人工核验 |

> **L1 的限制是刻意的。** 风险表明确列出「领域过于宽泛导致深度不足」。`domain` 字段若出现两个以上取值，说明学科聚焦还没完成 —— 此时应先停下来收敛方向，而不是继续加语料。

### 4.2 层级关系：树 + 图

前三层构成**树**（严格父子关系，一个知识点只属于一个子方向），第三到第四层是**引用**（一个知识点可引用多篇文献，一篇文献可被多个知识点引用）。而**跨知识点的依赖关系**叠加在这棵树上，构成有向图（§五）。

```text
domain（领域，1–2 个）
  └── sub_domain（子方向，3–6 个）          ← 树：严格父子
        └── knowledge_point（知识点）         ← 树：严格父子
              ├── source（文献，1–n）        ← 引用：多对多
              └── prerequisites（依赖）      ← 图：跨子树的有向边
```

**树的约束**：`domain` / `sub_domain` 的取值必须在 `knowledge/domains/` 的领域索引（`_index.md`）中登记后使用。**不允许**凭个人习惯随手新增子方向名称 —— 「大模型」和「大规模语言模型」被当作两个子方向，是知识库最常见的退化形式。

### 4.3 `knowledge_point` 与 `id` 的对应

- `knowledge_point` 是**人名**（可读的中文名，如「自注意力机制」）
- `id` 是**学号**（`kn-NNNN`，全库唯一，永不复用）

两者一一对应，但职责不同：`prerequisites` 与 `data/route/*.json` 的 `edges` 一律引用 `id`，而人读的文档用 `knowledge_point`。**改名不改 id** —— 知识点更名时只改 `knowledge_point`，`id` 保持稳定，以免打断所有引用它的依赖边。

> `id` 分配规则：按入库顺序递增，`kn-0001` 起。**不按层级编号**（不要用 `kn-1001` 表示子方向 A），因为层级会调整而 id 不能变。

### 4.4 与 Web 路线图的对应

`data/route/*.json` 的 `stages[].knowledge_points[].kp_id` 直接对应 `domains/` 知识单元的 `id`。因此：

- 知识点尚未入库时，不得出现在路线数据中（否则 Web 侧图节点无出处，违反「所有条目标注出处链接」）；
- 知识点被下线（§七）时，必须同步清理路线数据中的引用。

## 五、依赖关系模型（本规范核心）

架构书三(四)与八章都把知识点依赖建模列为「**本项目知识库设计相比普通文档库的核心差异**」，以及「技术创新性」评分的支撑点。因此这一节写得比其他部分更细。

### 5.1 依赖关系是什么

依赖关系回答一个问题：**要学会知识点 B，必须先掌握哪些知识点？**

形式化表示为有向边 `A → B`，语义为「A 是 B 的前置」，即 `B.prerequisites` 中包含 `A`。

> **方向约定（易错点）**：边从**前置**指向**后继**。
> `kn-0001 → kn-0005` 表示「先学 kn-0001，才能学 kn-0005」。
> 数据表达上，`prerequisites` 写在**后继**知识点的 front matter 里：`kn-0005` 的 `prerequisites: [kn-0001]`。
> 这两种表达是一致的，不是矛盾 —— 一个描述边的方向，一个描述字段的挂载位置。

### 5.2 三种关系类型

对应 `schemas/route.schema.json` 中 `edges[].relation` 的枚举（该 Schema 已由 SPEC-02 §4.2 定义）：

| `relation` | 含义 | 是否影响学习顺序 | 示例 |
| --- | --- | --- | --- |
| `prerequisite_of` | 强依赖：不掌握 A 无法理解 B | ✅ **影响**，路线生成据此排阶段 | 「线性代数基础」→「注意力机制的矩阵形式」 |
| `related_to` | 弱关联：两者常配合使用，但无先后要求 | ❌ 不影响，仅用于知识图谱展示与推荐 | 「LayerNorm」↔「残差连接」 |
| `extends` | 延伸：B 是 A 在某一方向上的深化 | ✅ 影响，但可跳过 | 「自注意力」→「稀疏注意力」 |

**建边规则**：

1. `prerequisite_of` 必须**可辩护** —— 建边人要能回答「为什么没有 A 就学不会 B」。答不出来，就应改成 `related_to`。
2. `related_to` 是**对称**的（A↔B 与 B↔A 等价），存储时只存一条，方向按 `id` 升序。
3. `extends` 不构成学习路线的**必经**环节，路线生成时应作为「可选深入」标注。

### 5.3 建边流程与责任

依赖边是**人工判断 + AI 辅助核查**的产物，不能由 AI 直接生成后入库（SPEC-04 §3.3 明确知识库内容的审核要求）。

| 步骤 | 动作 | 负责角色 |
| --- | --- | --- |
| 1 | 提炼新知识点时，作者**先自查**：学这个之前需要什么？ | 知识库负责人 |
| 2 | 在 `prerequisites` 中填写候选 `id` 列表 | 知识库负责人 |
| 3 | 运行 `python scripts/check_knowledge_units.py` 做机器校验（环、悬空 id、方向） | 自动 |
| 4 | 人工复核每条新边的 `prerequisite_of` 是否可辩护 | 知识库负责人 |
| 5 | 同步更新 `data/route/` 的 `edges`（由脚本导出，不手工编辑） | 自动 + Web 负责人 |

### 5.4 防环：为什么必须有，怎么保证

**循环依赖会直接摧毁路线生成能力。** 若 `kn-0001 → kn-0002 → kn-0001`，路线规划智能体无法确定先学哪个，只能报错或输出退化顺序。SPEC-02 §3.2 已明文规定「**不得出现循环依赖**」。

本规范把它变成可自动检测的强约束：

| 检测项 | 规则 | 违反后果 |
| --- | --- | --- |
| **环检测** | 在 `prerequisite_of` 与 `extends` 构成的子图上做拓扑排序；存在环即失败 | 提交被 `check_knowledge_units.py` 拦截 |
| **悬空引用** | `prerequisites` / `edges` 中的每个 `id` 必须存在于 `domains/` | 同上 |
| **自环** | 知识点的 `prerequisites` 不得包含自身 | 同上 |
| **重复边** | 同一对 `(from, to, relation)` 不得重复 | 同上 |

对应架构书三(4)的 `configs/afn.config.yaml` 已有配置项：

```yaml
knowledge_base:
  organization:
    build_dependency_graph: true
    detect_cycles: true      # ← 本规范 §5.4 的落地开关
```

> **`detect_cycles: true` 的含义**：巡检脚本在 CI 与本地提交前都会跑拓扑排序。这条不只是文档要求，是**实际拦截**。

### 5.5 依赖图的两个消费方

建好的依赖图有两个直接消费方，这决定了它的数据质量要求：

| 消费方 | 用途 | 数据质量要求 |
| --- | --- | --- |
| **路线规划智能体** | 按拓扑序把知识点分配到各阶段，保证「前置先于后继」 | `prerequisite_of` 必须准确；**漏边**会导致生成无法完成的路线 |
| **Web 路线图（ECharts 有向图）** | 图形化呈现依赖顺序（架构书四(2)） | `related_to` 也要有，否则图谱过于稀疏，看不出知识结构 |

> **漏边比多边更危险。** 多一条 `related_to` 只是图谱多一条线；漏一条 `prerequisite_of` 会让路线生成把「注意力机制」排到「线性代数」之前，直接产出不可用的学习路线。**建边时宁可保守多建 `related_to`，不要漏 `prerequisite_of`。**

## 六、语料准入标准

架构书三(4)给出四项准入标准：「来源**可公开访问**、有**明确作者与出处**、属于该领域的**奠基性或代表性成果**、**时效性**满足要求。低质量或来源不明的语料不入库。」

这一节把四项标准细化为**可判定的量表**，并逐库给出具体阈值 —— 否则「奠基性」这种词在实操中无法裁决。

### 6.1 通用准入：四维量表

每条候选语料按四个维度打分，**四项全部达到最低要求方可入库；任一维度不达标即拒绝**（不做加权平均 —— 一票否决制，因为出处不明的语料风险无法被其他维度的优秀抵消）。

| 维度 | 对应架构书标准 | 判定问题 | 最低要求 | 不合格表现 |
| --- | --- | --- | --- | --- |
| **A 可访问性** | 来源可公开访问 | 链接能否在没有账号、没有付费墙的情况下打开？ | ✅ 匿名可访问，返回 200 | 需登录、需付费、链接失效、指向网盘临时链接 |
| **B 出处明确** | 有明确作者与出处 | 作者是谁？发表于哪？是原始文献吗？ | ✅ 作者 + 出处 + 年份三者齐全 | 「某博客」「佚名」「转载未注明来源」「AI 生成未标注」 |
| **C 权威性** | 奠基性或代表性成果 | 它在该子方向的地位如何？ | ✅ 见 §6.2 分级表 | 低质量会议、非同行评议的个人解读、营销内容 |
| **D 时效性** | 时效性满足要求 | 是否已过时？是否有更新的结论替代？ | ✅ 见 §6.3 分库阈值 | 结论已被推翻却未标注、超期未复核 |

### 6.2 C 维度：权威性分级

| 等级 | 材料类型 | `domains/` | `intelligence/` | 说明 |
| --- | --- | --- | --- | --- |
| **C1 奠基性** | 开创性论文、经典教材 | ✅ 优先收录 | — | 定义了一个子方向的工作 |
| **C2 代表性** | 顶会/顶刊论文、权威综述、知名公开课 | ✅ 收录 | ✅ 收录 | 被广泛引用的工作 |
| **C3 一般性** | 普通会议论文、技术博客、社区文档 | ⚠️ 需谨慎，须标注局限 | ✅ 可收录 | 仅在有明确价值时收 |
| **C4 参考性** | 开源项目文档、工具使用说明 | ✅ 作为 `doc` 类来源收录 | — | 服务于工程实践，非学术结论 |
| **C5 不可采信** | 来源不明、AI 生成未标注、营销内容、二手转述 | ❌ 拒绝 | ❌ 拒绝 | **无例外** |

> **C5 的一票否决是硬红线。** SPEC-04 §3.3 已明确：「让 AI 编造文献信息 → **严重违规**。`source.url` 必须真实可访问。」C 维度不达标不仅是质量问题，更是合规问题。

### 6.3 D 维度：各库时效性阈值

| 库 | 时效要求 | 复核周期 | 说明 |
| --- | --- | --- | --- |
| `domains/` | **无硬性年限**，但需通过「三年后是否成立」检验 | 每 **6 个月**复核一次 | 经典论文不受年限限制；教材需关注是否有新版 |
| `intelligence/` | 抓取窗口 `lookback_days`（默认 7 天） | 每次抓取即复核 | 超窗内容不入选 |
| `personal/` | 无年限要求 | 随用户学习推进自然更新 | 个人笔记的价值随时间增长 |

> **`domains/` 为什么设复核周期**：不设的话，知识库会单向往「只增」演化，逐渐堆入已被领域淘汰的内容。6 个月是与 10 天交付周期相称的合理值 —— 决赛阶段如继续迭代，这个周期会真正触发一次。

### 6.4 分库准入清单

#### （一）`domains/` 领域知识库

| 检查项 | 要求 |
| --- | --- |
| `source.url` 匿名可访问 | ✅ 人工逐一打开确认（SPEC-04 §3.3 强制） |
| `source.authors` 非空 | ✅ 至少一位作者 |
| `source.published_date` | ✅ 尽量填写；教材可填版次年份 |
| 权威性等级 | ✅ C1 / C2 / C4；C3 需在正文标注局限 |
| `id` 唯一 | ✅ `kn-NNNN` 格式，未与既有重复 |
| `prerequisites` 无环 | ✅ 由脚本校验 |
| 正文有「参考来源」段 | ✅ SPEC-02 §3.2 要求 |
| 粒度正确 | ✅ 一个知识点，非一篇论文的搬运 |

#### （二）`intelligence/` 动态情报库

| 检查项 | 要求 |
| --- | --- |
| `source.url` 可访问 | ✅ |
| `relevance` 已分层 | ✅ `high` / `medium` / `low` |
| `relevance_reason` 非空泛 | ✅ 必须与用户研究方向关联，不得写「与方向相关」 |
| `quick_read` 已生成 | ✅ 一句话中文速读 |
| 时间窗口内 | ✅ `published_date` 落在 `time_window` 内 |
| 幂等 | ✅ 文件名 `briefing-YYYY-MM-DD.json`，同日覆盖 |
| 不得混入 `domains/` 内容 | ✅ 已通过时间检验的内容应另行提炼 |

#### （三）`personal/` 个人资产库

| 检查项 | 要求 |
| --- | --- |
| 结构化程度 | ✅ 已提炼为结论，非原始对话流水 |
| `visibility` | ✅ 默认 `private`（架构书六(2)：默认私密） |
| `origin` 可溯源 | ✅ 记录来源类型与 `ref` |
| **脱敏** | ✅ 仓库内只提交 `*.example.md`；真实数据被 `.gitignore` 屏蔽 |
| 不侵犯原文版权 | ✅ 引用与转述，不搬运全文 |

### 6.5 出处核验的强制流程

SPEC-04 §3.3 规定：「`knowledge/domains/` 下每个知识单元的 `source` 字段，**必须由人工逐一访问 `url` 确认可达且内容匹配**。这条规则没有例外。」

落地为一个可执行的四步：

```text
① 打开 source.url（匿名窗口，无登录态）
      ↓ 返回 200 且页面标题与 source.title 一致
② 核对作者与年份
      ↓ 与 source.authors / published_date 一致
③ 确认内容确实支撑该知识点
      ↓ 页面内容与 knowledge_point 描述相符，非张冠李戴
④ 在 iteration-log 记录核验时间与核验人
```

> **为什么要用匿名窗口**：本项目成员若已登录某学术平台，链接可能在登录态下可访问，但评审或用户访问时会 403。**只以匿名态为准。**

### 6.6 拒绝与例外

| 情况 | 处理 |
| --- | --- |
| 四维任一不达标 | ❌ 拒绝入库，不设例外 |
| 语料质量存疑但确有必要 | ⚠️ 可入库，但**必须在正文显式标注局限**，并在 `tags` 中加 `待复核` |
| 链接暂时不可访问（如站点维护） | ⏸ 暂缓入库，不降级处理 |
| 已入库语料被发现不合格 | → 走 §七 退出机制 |

架构书原文「**低质量或来源不明的语料不入库**」是拒绝的最终依据。

## 七、复核与退出机制

准入不是一次性的。已入库的语料需能**被撤回** —— 缺少退出机制的知识库会持续劣化。

### 7.1 触发复核的三种情形

| 情形 | 触发条件 | 处理时限 |
| --- | --- | --- |
| **周期复核** | 距上次复核满 6 个月（`domains/` 适用） | 3 日内完成 |
| **链接失效** | 巡检脚本或人工发现 `source.url` 返回非 200 | 立即 |
| **内容过时** | 出现新的代表性成果推翻或大幅修正原结论 | 1 周内 |

### 7.2 三种处置方式

| 处置 | 适用 | 操作 | 是否可逆 |
| --- | --- | --- | --- |
| **更新** | 链接迁移、有新版本 | 修正 `source.url`，同步更新 `updated_at`；`id` 不变 | ✅ |
| **降级** | 结论被部分修正，但仍具方法论价值 | 正文补充「⚠️ 局限」段落，`tags` 加 `已有更新`，保留在库 | ✅ |
| **下线** | 结论已被推翻，或出处无法核验 | 从 `domains/` 移出；**`id` 不复用**；同步清理 `data/route/` 中的引用 | ❌ 不可逆 |

### 7.3 下线时的一致性要求

下线一个知识点会牵动三处，**必须同时处理**，否则会留下悬空引用：

```text
① knowledge/domains/<知识点>.md          ← 移出（或移入归档区）
② 其他知识单元的 prerequisites            ← 清理指向它的边
③ data/route/*.json 的 stages 与 edges    ← 清理引用（由脚本重新导出）
```

> **记住：`id` 永不复用。** 即使 `kn-0007` 被下线，后继新知识点也用 `kn-00xx` 的下一个未用号，不得回收 `kn-0007`。这与 ADR 的编号规则同理（SPEC-03 §6.4）—— 复用会让历史引用指向错误的内容。

### 7.4 复核记录

每次复核在 `iteration-log/` 留痕，记明：复核日期、复核人、涉及知识点、发现的问题、处置方式。**即使复核结论是「全部通过」也要记录** —— 这证明复核真的做了。

## 八、检索口径约定

知识库建好后由智能体消费。为保证检索结果不被噪声污染，约定以下口径：

| 约定 | 内容 | 依据 |
| --- | --- | --- |
| **分层检索** | `domains/` 优先于 `intelligence/`：涉及「概念是什么」的问题只检索 `domains/` | 架构书三(四)服务对象划分 |
| **个人库隔离** | `personal/` 只在用户本人会话中检索，不参与跨用户的通用问答 | 架构书六(一)访问控制 |
| **出处随行** | 检索结果的每条命中都必须能带出 `source.url` | 架构书六(2)出处标注 |
| **无据不答** | 检索无命中时，智能体必须显式声明知识边界，不得推测 | 架构书六(2)知识边界声明 |
| **时效标注** | `intelligence/` 的命中必须显示 `published_date`，避免用户把 7 天前的动态当现状 | 架构书四(2)相关性分层 |

> **「无据不答」是本项目对比通用问答工具的关键差异点之一**，已写入 `prompts/principle/` 原则层。知识库的检索接口设计必须支持「无命中」这一返回值，不能设计成「总要给点东西」。

用 `configs/afn.config.yaml` 的现有配置守住准入底线：

```yaml
knowledge_base:
  ingestion:
    require_source_url: true        # 无 url 不入库
    require_public_access: true     # 不可公开访问不入库
    reject_unknown_origin: true     # 出处不明不入库
```

这三条恰好对应 §6.1 的 A、B 两维，把「能不能进」的第一道关交给配置而非人力。

## 九、落地检查清单

### 新建知识单元时

- [ ] 用 §3.1 三问确认应放 `domains/`，而非 `intelligence/` 或 `personal/`
- [ ] 粒度正确：一个知识点，不是一篇论文
- [ ] `domain` / `sub_domain` 取值已在领域索引中登记
- [ ] `id` 为 `kn-NNNN` 格式且全库唯一（**不复用已下线 id**）
- [ ] `source` 四维全部达标（§6.1）
- [ ] `source.url` 已**用匿名窗口**打开确认可达且内容匹配（§6.5）
- [ ] 正文含「参考来源」段

### 建立依赖关系时

- [ ] 边方向为「前置 → 后继」，`prerequisites` 写在后继知识点上
- [ ] `prerequisite_of` 每条都能回答「没有 A 就学不会 B」
- [ ] `related_to` 只存一条，方向按 `id` 升序
- [ ] 已运行 `python scripts/check_knowledge_units.py` 且通过（无环、无悬空、无自环）

### 提交前

- [ ] 文件为 UTF-8 无 BOM、LF 换行、末尾一个空行（SPEC-02 §2.1）
- [ ] 三库无混放
- [ ] `personal/` 下无真实个人数据，仅有 `*.example.md`
- [ ] 已更新领域索引与 `CHANGELOG.md`

### 复核时

- [ ] 距上次复核未超 6 个月
- [ ] 全部 `source.url` 仍可达
- [ ] 无结论被推翻却未降级/下线的条目
- [ ] 复核过程已在 `iteration-log/` 留痕（包括「全部通过」的结论）
