## 一、背景

架构书三(四)规定知识库「按『领域 → 子方向 → 知识点 → 文献』的层级组织，并标注知识点之间的依赖关系」，八章把「知识点的依赖关系建模」列为「技术创新性」的支撑点。

但架构书只给出了**结论**，未说明依赖关系的**技术形态**。落地时必须回答三个问题：

1. 依赖关系存成什么格式？
2. 谁来判断两个知识点之间的依赖？
3. 出现循环依赖怎么办？

这三个问题不解决，「依赖关系建模」会退化为文档里的一句话，而非可被路线生成真正消费的数据。

### 约束条件

- 交付周期仅 **10 天**，且知识库是全部智能体能力的地基，须在第 2 天产出最小可用版本
- 架构书五(三)已排除重型前端框架与自建后端，依赖关系必须能被**静态 JSON + 原生 JS** 直接消费
- 团队成员无图数据库经验，引入 Neo4j 等方案不具备可行性
- 依赖关系的准确性是路线生成质量的上限 —— 计划书风险表已将「知识库语料质量」列为**最高风险点**

---

## 二、决策

> **决策**：依赖关系以**知识点 front matter 的 `prerequisites` 字段**为唯一事实来源，存储为有向图，并通过脚本强制校验无环；同时导出一份显式边表 JSON 供 Web 与路线生成消费。

### 具体内容

**1. 数据存放：双形态，单一来源**

| 形态 | 位置 | 角色 |
| --- | --- | --- |
| **事实来源** | `knowledge/domains/**/*.md` 的 `prerequisites` | 人工维护，写在**后继**知识点上 |
| **导出形态** | `knowledge/domains/_graph.json` | 由脚本生成，含 `nodes` + `edges` |

**2. 边方向的约定**

`A → B` 表示「A 是 B 的前置」。数据表达上，`A` 写在 `B` 的 `prerequisites` 里：

```yaml
# kn-0006 的 front matter
prerequisites: [kn-0005, kn-0008, kn-0009]
```

**3. 三种关系类型**（对应 `schemas/route.schema.json` 的 `relation` 枚举）

| `relation` | 影响学习顺序 | 用途 |
| --- | --- | --- |
| `prerequisite_of` | ✅ 影响 | 路线生成的拓扑依据 |
| `related_to` | ❌ 不影响 | 仅用于知识图谱展示与推荐 |
| `extends` | ✅ 影响（可跳过） | 标注可选深入方向 |

**4. 强制校验：环、悬空引用、自环**

`scripts/check_knowledge_units.py` 对 `prerequisite_of` 与 `extends` 构成的子图做 **Kahn 拓扑排序**，存在环即返回非零退出码，阻止提交。对应 `configs/afn.config.yaml` 的既有开关：

```yaml
knowledge_base:
  organization:
    detect_cycles: true
```

## 三、理由

1. **front matter 作为事实来源，避免双写不一致。**
   若单独维护一个依赖关系表，就出现了两份需要同步的数据，而 10 天周期下必然出现漂移。写在知识点自身文件里，改知识点与改依赖是**同一次提交**，天然原子。

2. **导出的边表让下游不必解析 Markdown。**
   SPEC-02 §一已明确「依赖关系是结构化数据，应为 JSON」。若让 Web 侧从前端解析 `prerequisites`，就违反了该约定的「反面案例」——用正则解析本该是结构化的数据。显式 `edges` 数组让 ECharts 可直接作为有向图输入。

3. **方向约定写在后继上，符合人的思维顺序。**
   建边时的自然提问是「要学这个，我需要先会什么」，这句话的主语是**后继**。把 `prerequisites` 写在后继的 front matter 里，与提问方式一致，降低建边出错率。

4. **拓扑排序是唯一可靠的防环手段。**
   人工检查在 15 个节点时勉强可行，但节点数增长后必然失效 —— 环往往由「A 依赖 B」和「B 依赖 C」两次看似独立的修改共同引入，任何单次修改都看不出问题。**机器校验是唯一可行方案。**

5. **不引入图数据库，符合技术栈边界。**
   15–60 个节点的图规模，JSON + 内存内拓扑排序完全够用。引入 Neo4j 会同时触碰架构书五(三)的两条排除项（自建后端、生产级基础设施）。

## 四、备选方案

| 备选方案 | 优点 | 未采用的原因 |
| --- | --- | --- |
| **在 Markdown 正文中用文字描述依赖** | 无需新字段 | 违反 SPEC-02 §一「依赖关系是结构化数据，应为 JSON」；下游需正则解析，脆弱且丢失溯源 |
| **单独维护 `dependencies.yaml` 依赖表** | 集中查看方便 | 双写：改知识点与改依赖分属两次提交，10 天周期下必然漂移 |
| **引入图数据库（Neo4j 等）** | 查询能力强 | 触碰架构书五(三)排除项；15 个节点规模严重过度设计 |
| **由 AI 自动生成依赖边** | 节省人力 | 违反 SPEC-04 §3.3 知识库内容须人工审核的要求；且依赖边的「可辩护性」无法由 AI 保证 |
| **不建模依赖，路线按难度线性排序** | 实现最简 | 直接放弃架构书列为「核心差异」与评分支撑点的能力；且无法正确生成多起点并行的路线 |

## 五、影响

### 正面影响

- 依赖关系成为**可校验的数据**而非文档描述，漏边与环能在提交前被发现
- 路线生成获得可靠的拓扑依据，`kn-0006` 这类三前置汇聚节点不会被错误排序
- Web 侧可直接消费 `edges` 画有向图，无需解析 Markdown
- 「知识点的依赖关系建模」在评审中可展示为**可运行的校验脚本**，而非口头声明

### 负面影响与代价

- **建边成本转嫁到人工**：每条 `prerequisite_of` 都需要人判断并保证可辩护，比不建模多一道工序
- **`related_to` 的对称性需人工遵守**：只存一条、方向按 `id` 升序，是约定而非强制，脚本目前只能检测重复不能检测方向错误
- **知识点更名时 `id` 不能变**：需要通过文档约束（SPEC-06 §4.3），否则会打断所有引用边
- **漏边无法被脚本发现**：脚本只能发现悬空引用与环，**漏建一条本该存在的边是检测不到的**。这依赖人工复核
